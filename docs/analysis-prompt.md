# 시안 분석 프롬프트 — 설계 근거

시안 이미지를 입력받아 학습 콘텐츠(구조 · 판정 조건 · 모범 예시)를 생성하는 프롬프트의 **설계 근거**를 기술합니다.

> **문서 관리 규칙**
>
> **실행되는 프롬프트 문자열의 출처는 `lib/ai/prompts.ts`입니다.** 본 문서는 그 설계 근거를 기술하며, 프롬프트 전문이나 출력 JSON 예시를 옮겨 적지 않습니다.
>
> 이 프로젝트에서 반복해 어긋난 지점은 전부 사본이었습니다. 조건 유형 목록, rubric 스키마, 검증 체크리스트가 모두 같은 이유로 한 버전 만에 갈라졌습니다. 실행되는 것과 설명하는 것을 분리합니다.
>
> 조건 유형 목록은 PRD §4.6.4, 출력 필드 형태는 PRD §6.3이 출처이며, 프롬프트 문자열은 이를 구현합니다.

---

## 호출을 3단계로 나눈 이유

```
1단계  구조 분석      이미지 → 구역 · 의미 구조 · mainTitleSectionId
2단계  조건 생성      1단계 출력 → rubric
3단계  모범 예시      2단계 출력 → example html/css
```

**한 호출에서 모범 예시와 조건을 동시에 생성하면, AI가 자기가 쓴 코드를 설명하는 조건을 만듭니다.** 그러면 "예시 코드와 다르면 오답"이라는 결과가 되어 다양성 대응이 무너집니다. 조건을 먼저 확정하고, 그 조건을 만족하는 예시를 나중에 만들어야 순서가 맞습니다.

2·3단계는 **구역 확정 이후에** 실행합니다. 사용자가 구역을 병합·분할하면 먼저 만든 조건이 확정된 구역과 어긋나기 때문입니다. 상세는 PRD 3장을 참조하십시오.

---

## 1단계 — 구조 분석

### 태그와 CSS 이름을 쓰지 않게 하는 이유

구조 트리에 `nav`나 `flex`가 들어가면 학습자가 훈련해야 할 판단을 미리 정해버리는 셈입니다. 역할로만 기술하게 하고, 배치는 결과("가로 한 줄", "3개씩 2행")로 적게 합니다.

### 격자 구조를 평면으로 세게 하는 이유

**모호성이 1단계에서 확정되면 2단계의 `accept` 다중 해석이 무력화됩니다.**

타일 6개가 2열 3행일 때 1단계가 "행 3개, 각 행에 2개"로 중첩 구조를 만들면, 2단계는 받은 트리에 행 계층이 있으므로 평면 해석이 존재한다는 것을 알 수 없습니다. 나열할 재료가 없는 것입니다.

8.3 재현성 검증에서 3회차가 `list-grouping`(그룹 3개)과 `layout-result`(행 계층 포함)를 **함께** 낸 것이 이 진단의 근거였습니다. 2단계가 독립적으로 두 번 오판했다기보다 1단계 트리에 이미 행 계층이 있었다고 보는 편이 자연스럽습니다.

따라서 1단계는 항목을 평면으로 세고 배치를 `columns`/`rows`로만 기술합니다. 반복 단위를 행으로 볼지 항목으로 볼지는 2단계가 판단합니다.

### `mainTitleSectionId`를 별도 필드로 받는 이유

문서 전체 범위 조건(`heading-single`, `heading-order`)의 검사 시작 구역을 결정하는 값입니다(PRD F-08-10).

구조 트리의 `role`은 자유 서술 문자열이고 태그명 사용이 금지되어 있어 제목 레벨을 표현할 수단이 없습니다. 엔진이 문자열을 해석해 시작 구역을 추정하면 F-02-12(문자열 미의존)와 어긋나므로 전용 필드로 받습니다.

판단이 서지 않으면 `null`을 반환하게 하고, 스키마 검증에서 거부해 재생성을 요청합니다.

## 2단계 — 판정 조건 생성

### 화이트리스트 주입

조건 유형 목록은 `{{CONDITION_TYPES}}` 자리에 런타임 주입합니다. 프롬프트 문자열에 목록을 하드코딩하지 않습니다.

주입 텍스트와 스키마 검증용 열거형은 **하나의 상수에서 파생**되어야 합니다(F-02-15). 둘을 따로 정의하면 "프롬프트가 제시한 유형"과 "검증이 통과시키는 유형"이 어긋날 수 있습니다.

엔진이 상시 검사하는 유형(`heading-single`, `heading-order`)과 보류 유형은 주입 표에서 제외합니다. 표에 넣어두고 "생성하지 마십시오"라고 덧붙이는 것보다 애초에 보이지 않는 편이 어긋날 여지가 적습니다.

### 다중 해석 허용 — `list-grouping` 전용

2차원 격자에서 반복 단위는 "항목 6개의 평면 나열"과 "행 3개, 각 행에 2개"로 갈립니다. **시안 이미지만으로는 어느 쪽인지 알 수 없으며 둘 다 올바른 구현입니다.** 하나를 고르면 다른 해석으로 맞게 작성한 학습자가 오답 처리됩니다.

**`accept` 제약:** 항목이 늘어날수록 조건은 약해지므로, 모든 항목은 동일한 시각적 결과를 낳는 구현이어야 합니다. 시각적 결과가 다른 해석을 나열하는 것은 조건 무력화입니다.

**`layout-result`에는 적용하지 않습니다.** 중첩 배치와 평면 배치는 렌더된 말단 요소의 좌표가 같으므로 판정 단계에서 자동으로 흡수됩니다(PRD §4.6.5). 여기에 여러 해석을 나열하면 조건만 약해집니다. accept는 항상 1개이며 기대값은 말단 요소의 기하로만 기술합니다.

### 배치 조건을 결과로만 기술하게 하는 이유

"그리드로 배치할 것"처럼 구현 방식을 조건화하면 렌더 결과 판정의 이점이 사라집니다. Flex·Grid·float의 차이가 자동으로 해소되는 것이 이 설계의 핵심이므로, 조건은 "타일 6개가 가로 2개씩 3행으로 놓일 것"처럼 결과로만 적어야 합니다.

### 판단이 갈리는 사항은 전부 권장 이하

요소 선택(section/article/div), 목록 표현(ul+li 대 div+article), 링크와 버튼, 클래스 이름 등은 어느 쪽도 틀리지 않습니다. 필수로 만들면 오탐이 됩니다.

## 3단계 — 모범 예시 생성

확정된 조건을 만족하는 코드를 작성하게 합니다. 읽기 쉽고 관행적인 코드를 요구하며, 프레임워크와 주석을 금지합니다.

---

## 검증 항목

프롬프트를 시험할 때 확인할 것들입니다.

### 화이트리스트 준수

- [ ] 필수 조건의 `type`이 **주입된 유형 목록** 밖으로 나가지 않는가 (개수를 하드코딩하지 말 것)
- [ ] 요소 선택(section/div 등)이 필수로 올라오지 않는가
- [ ] ul+li 대 div+article 판단이 필수가 아닌가

### 조건 서술 방식

- [ ] `layout-result` 조건에 CSS 속성명이 들어가지 않는가
- [ ] 조건이 결과로 기술되었는가
- [ ] `layout-result`의 `accept`가 1개인가 (2개 이상이면 위반)
- [ ] `layout-result`의 기대값이 말단 요소의 기하로만 기술되었는가 (DOM 중첩 구조가 섞이지 않았는가)
- [ ] `list-grouping`의 `accept` 항목들이 모두 동일한 시각적 결과를 낳는 구현인가

### 구조 분석

- [ ] `structure`에 HTML 태그명이 섞이지 않는가
- [ ] 반복 항목의 개수가 정확한가
- [ ] 구역 경계가 시각적 구분과 일치하는가
- [ ] 격자 구조를 평면으로 세는가 (행 계층을 만들지 않는가)

### 재현성

같은 시안을 3회 분석했을 때

- [ ] 구역 개수가 같은가
- [ ] 필수 조건의 **`(type, 파라미터)` 집합**이 같은가
- [ ] 다르다면 어느 정도 차이인가

**비교 단위 주의 (PRD §8.3)**

개수와 유형만 비교하면 안 됩니다. 판정 결과를 좌우하는 것은 유형과 파라미터의 조합입니다.

| 사례 | 개수·유형 기준 | 실제 |
|---|---|---|
| 3회 모두 `layout-result` 1개, 기대값이 "2열 3행 / 2열 3행 / 3열 2행" | 재현 성공 | **실패 — 판정이 뒤집힘** |
| 3회의 `desc` 문구가 모두 다르나 `(type, 파라미터)`는 동일 | 실패 | **성공 — 판정 동일** |

`desc`는 판정에 관여하지 않으므로 문구 차이는 불일치로 세지 않습니다.

### 3단계 정합성

- [ ] 생성된 예시가 2단계 조건을 실제로 만족하는가
- [ ] 만족하지 않는다면 조건이 잘못된 것인지 예시가 잘못된 것인지

---

## 확인된 사항

**구역 경계 좌표의 정확도 — 1차 확인 완료.** 1200×1600 시안에서 경계가 명확한 두 지점(헤더 하단 구분선, 푸터 배경 시작)의 오차가 각각 2px이었습니다. 오버레이가 어긋나 사용자가 매번 조정해야 하는 수준은 아닙니다. 다른 시안에서의 재확인은 필요합니다.

**격자 평면 고정 — 작동 확인.** 상품 6개를 `repeat: 6`, `columns: 3`, `rows: 2`로 읽고 행 계층을 만들지 않았습니다.

**구조 트리의 태그·CSS 이름 배제 — 작동 확인.** 금지어 검사에서 0건이었습니다.

---

## 알려진 미해결 사항

**재현성 확보 방안이 없습니다.** 온도를 낮춰도 완전히 같은 출력을 보장하지 못합니다. 현재 설계는 "분석은 1회만 하고 결과를 저장"하므로 한 시안 안에서는 일관성이 유지되지만, 재분석 시 조건이 달라집니다. 재분석 기능을 넣을지, 넣는다면 기존 진행 상태를 어떻게 처리할지 미정입니다.

**구역 편집 후의 구조 트리 정합성이 미정입니다.** 사용자가 구역을 분할하면 1단계가 만든 구조 트리는 원래 구역 기준이므로 새 구역과 어긋납니다. 2단계에 이미지를 함께 넘겨 다시 읽게 할지, 다른 방식으로 처리할지 정해야 합니다.
