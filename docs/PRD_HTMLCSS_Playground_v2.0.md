## 1. 개요

### 1.1 한 줄 정의

사용자가 등록한 웹 디자인 시안을 AI가 분석하고, 사용자가 직접 HTML/CSS를 작성해 시맨틱 마크업과 레이아웃 구현 능력을 훈련하는 웹 기반 학습 도구.

### 1.2 배경

HTML/CSS 학습에서 문법은 자료가 충분하지만, "이 화면을 어떤 구조로 마크업할 것인가"에 대한 판단력은 실전 반복 없이는 길러지지 않습니다. 기존 코딩 챌린지 플랫폼은 정해진 시안만 제공하므로 학습자가 원하는 디자인으로 연습할 수 없고, 피드백도 커뮤니티 리뷰에 의존해 즉시성이 떨어집니다.

본 도구는 **사용자가 원하는 시안을 직접 등록**하고 **즉시 구조적 피드백**을 받는 환경을 목표로 합니다.

### 1.3 학습 목표 (Scope의 기준)

본 도구가 훈련시키는 대상은 다음 두 가지로 한정합니다.

1. **시맨틱 마크업** — 콘텐츠의 의미에 맞는 HTML 요소 선택, 문서 구조의 논리적 계층 구성
2. **레이아웃 구현** — 시안의 배치 관계를 CSS로 재현하는 능력

### 1.4 비목표 (Non-goals)

다음은 **의도적으로 다루지 않습니다.**

| 항목 | 제외 사유 |
|---|---|
| 픽셀 단위 정확도 | 학습 목표와 무관. 간격 2px 차이는 시맨틱·레이아웃 실력과 관계없음 |
| 폰트 이름 일치 | 시안에서 정확히 판별 불가하며 학습 가치 낮음 |
| 인터랙션 (hover, 애니메이션) | 별도 학습 영역. 향후 확장 후보 |
| JavaScript | 범위 외 |
| 반응형 브레이크포인트 | v1 범위 외. 향후 확장 후보 |
| 코드 스타일 (들여쓰기, 클래스 네이밍) | 판정 대상 아님 |
| 다크 모드 | 미리보기 영역은 사용자 CSS만 적용되므로 항상 밝은 배경으로 남음. 다크 UI 내 흰 패널 구성이 되어 실익이 낮고, 색 토큰·에디터 테마를 이중 관리해야 함. 시안과 결과를 눈으로 비교하는 동작에도 불리. **단, 색상은 CSS 변수로 정의하여 향후 도입 가능성을 열어둠** |

## 2. 사용자 정의

### 2.1 주 사용자

- HTML/CSS 문법은 알지만 실제 시안을 보고 구조를 잡는 데 어려움을 겪는 학습자
- 퍼블리싱 입문자 및 전환자
- 시맨틱 태그를 알지만 실무에서 언제 무엇을 쓸지 판단이 서지 않는 사용자

### 2.2 사용 맥락

- 개인 학습용. 다중 사용자 협업·평가 기능은 범위 외
- 반복 연습 도구. 1회성 테스트가 아님

## 3. 핵심 사용자 흐름

```
[1] 소스 등록
     ├─ 이미지 업로드 (PNG/JPG) 또는 Figma 파일·링크
     ├─ 학습 모드 선택 (통짜 / 구역별)
     └─ 시도 횟수 설정 (1~5회)
              ↓
[2] AI 분석 (1회, 결과 영구 저장)
     ├─ 의미 구조 트리 추출
     ├─ 배치 관계 추출
     ├─ 판정 조건 생성 (필수/권장/자유)
     └─ 구역 분할 (구역별 모드일 때만)
              ↓
[3] 구역 확인 및 조정 (구역별 모드, 별도 화면)
     ├─ 시안 위 오버레이로 AI 분할 결과 확인
     ├─ 병합 / 분할 / 경계 조정 (선택적)
     └─ 확정 후 학습 화면 진입
              ↓
[4] 코딩 + 실시간 미리보기 (반복)
              ↓
[5] 확인 요청 → 판정 → 회차별 피드백
     ├─ 통과 → 다음 구역 또는 완료
     └─ 미통과 → 시도 횟수 차감 → [4]로 복귀
              ↓
[6] 시도 소진 시 모범 예시 공개
```

**중요:** AI 호출은 [2]에서만 발생합니다. [4]~[6]은 저장된 분석 결과로 브라우저 내에서 처리되며 런타임 AI 호출이 없습니다.

**F-05-04 상세 — 숨김 방식 (중요)**

**판정용 iframe을 `display:none`으로 숨겨서는 안 됩니다.**

`display:none`은 레이아웃 박스를 생성하지 않으므로 모든 측정값이 0이 됩니다. 이때 오류는 발생하지 않으며, 모든 요소의 `top`이 0으로 동일해지므로 **배치가 전혀 맞지 않는 코드도 `layout-result` 조건을 전부 통과합니다.**

이는 오탐(정답을 오답 처리)과 반대 방향의 실패이며, 예외 없이 조용히 통과하므로 발견이 어렵습니다. 학습자는 잘못 작성한 코드를 정답으로 인식하게 됩니다.

| 숨김 방식 | 측정값 | 판정 |
|---|---|---|
| `display:none` | 전부 0 | **무조건 통과 (오작동)** |
| `visibility:hidden` | 정상 | 정상 |
| 화면 밖 배치 | 정상 | 정상 |
| 보이는 상태 (대조군) | 정상 | 정상 |

**채택: 화면 밖 배치** (`position:absolute; left:-10000px`)

`visibility:hidden`은 문서 흐름에서 자리를 차지하여 부모 레이아웃에 영향을 줄 수 있으므로 제외합니다.

**F-05-06 상세 — 측정 시점**

사용자 CSS의 배경 이미지나 크기가 지정되지 않은 `<img>`가 있는 경우, 리소스 로드 전후의 측정값이 달라집니다. iframe의 `load` 이벤트는 하위 리소스 로드까지 대기하므로 그 이후에 측정합니다.

웹폰트 로드 완료(`document.fonts.ready`)까지 대기하는 방안도 있으나, 폰트 일치는 비목표(1.4)이므로 적용하지 않습니다.

### 4.6 판정 (F-06)

**본 도구의 핵심이며 가장 높은 실패 위험을 가진 영역입니다.**

#### 4.6.1 기본 원칙

> **모범 예시 코드와 사용자 코드를 직접 비교하지 않습니다.**

동일한 시안에 대해 올바른 구현은 다수 존재합니다. 코드 대조 방식은 정답을 오답으로 판정하는 오류를 필연적으로 발생시킵니다. 따라서 판정은 **조건 목록 충족 여부**로 수행합니다.

#### 4.6.2 조건 3등급

| 등급 | 처리 | 예시 |
|---|---|---|
| **필수** | 미충족 시 지적, 통과 불가 | **4.6.4의 조건 유형 정의표가 유일한 출처입니다.** 이 문서 내 다른 위치에 필수 조건 목록을 중복 기재하지 않습니다 |
| **권장** | 통과시키되 안내 문구 표시 | 메뉴를 `div`로 감쌈 → `nav` 제안, 카드를 `div`로 구성 → `article` 제안 |
| **자유** | 판정하지 않음 | Flex/Grid 선택, 클래스 이름, 구조적으로 등가인 요소 선택, 코드 포맷 |

**설계 원칙: 필수 조건은 최소한으로 잡습니다.** 판단이 애매하면 권장으로, 더 애매하면 자유로 내립니다. 틀리지 않은 코드를 틀렸다고 판정하는 것이 가장 큰 실패입니다.

#### 4.6.3 필수 조건 화이트리스트 — 정책

**AI가 필수 조건을 자유롭게 정하도록 두지 않습니다.** 사전에 정의된 목록 안에서만 선택하게 하고, 목록 밖의 모든 판단은 권장 이하로 배치합니다. 오탐을 구조적으로 차단하기 위한 장치입니다.

**목록의 유일한 출처는 4.6.4의 조건 유형 정의표입니다.** 본 절을 포함해 문서 내 다른 위치에 목록을 중복 기재하지 않습니다. 구현 시 코드의 열거형도 4.6.4를 참조합니다.

**목록 밖 판단의 예시 (전부 권장 이하)**

| 판단 | 사유 |
|---|---|
| `nav` / `section` / `article` / `div` 선택 | 맥락에 따라 복수의 정답 존재 |
| `<ul><li>` 대 `<div><article>` | 양쪽 모두 타당 |
| 링크(`a`)인가 버튼(`button`)인가 | 동작에 따라 다름. 시안만으로 확정 불가 |
| 각주 번호의 `sup` 처리 | 선택 사항 |
| 캐러셀 인디케이터의 시맨틱 | 장식/컨트롤 판단이 갈림 |

**배치 조건의 서술 방식**

배치 조건은 반드시 **결과**로 기술해야 하며 **구현 방식**으로 기술해서는 안 됩니다.

| 잘못된 기술 | 올바른 기술 |
|---|---|
| "그리드로 배치할 것" | "타일 6개가 2열 3행 위치에 놓일 것" |
| "Flex로 가로 정렬할 것" | "카드 3개의 세로 위치가 동일할 것" |

구현 방식을 조건에 넣으면 렌더 결과 판정의 이점이 사라지고 오탐이 발생합니다.

#### 4.6.4 화이트리스트 강제 — 스키마 검증과 판정 로직 고정

**화이트리스트 준수를 프롬프트에만 의존하지 않습니다.** 두 개의 계층으로 강제합니다.

| 계층 | 역할 | 신뢰도 |
|---|---|---|
| 프롬프트 | AI가 올바른 조건을 생성하도록 유도 | 확률적 |
| 스키마 검증 | `type` 값이 열거형에 속하는지 검사 | 결정적 |
| **판정 로직 고정** | **`type`별 검사 내용을 코드로 정의** | **결정적** |

**스키마 검증만으로 불충분한 이유**

스키마 검증은 `type` 값만 확인하며 `desc`가 해당 유형의 정의에 부합하는지는 판단하지 못합니다. 검증 과정에서 실제로 다음 사례가 발견되었습니다.

```json
{ "type": "heading-order", "desc": "제품명이 구역 제목보다 하위 계층일 것" }
```

`heading-order`의 정의는 "제목 계층을 건너뛰지 않을 것"(`h1` → `h3` 금지)이나, 위 조건은 "상하 관계"라는 다른 검사를 기술하고 있습니다. `type` 값이 유효하므로 스키마 검증을 통과합니다.

**대응: `desc`는 판정에 관여하지 않습니다.**

`desc`는 학습자에게 표시할 문구이며, 실제 판정은 `type`에 대응하는 고정된 코드가 수행합니다. AI가 `desc`에 무엇을 쓰든 판정 동작은 변하지 않습니다.

**조건 유형 정의 (화이트리스트 단일 출처)**

| type | 검사 내용 | AI 제공 파라미터 | 채택 근거 |
|---|---|---|---|
| `heading-order` | 제목 요소의 레벨이 2 이상 건너뛰지 않는지 | 없음 | `h1` → `h3`은 명백한 오류 |
| `heading-single` | 문서 내 `h1`이 정확히 1개인지 | 없음 | 문서 구조의 기본 |
| `heading-hierarchy` | 지정된 두 요소의 제목 레벨 상하 관계 | 상위 대상, 하위 대상 | 구역 제목이 항목 제목보다 상위여야 함 |
| `image-alt` | 의미 있는 이미지에 `alt`가 존재하는지 | 대상 이미지 식별자 | 접근성 필수 요건 |
| `list-grouping` | 반복 항목이 목록 요소로 묶였는지 | 반복 개수, 대상 | 목록 요소의 정의에 부합 |
| `form-label` | 폼 컨트롤에 레이블이 연결되었는지 | 대상 컨트롤 | 접근성 필수 요건 |
| `layout-result` | 렌더 측정값이 기대 배치와 일치하는지 | 기대 배치 (행/열, 정렬 등) | 측정 가능한 객관적 기준 |

`heading-hierarchy`는 8.3 검증에서 발견된 유형으로, 조건 자체가 타당하므로 정식 추가되었습니다.

**유형 추가 시 주의:** 본 표가 화이트리스트의 유일한 출처입니다. 유형을 추가하거나 변경할 때 다른 절의 목록을 함께 수정할 필요가 없어야 하며, 만약 그런 상황이 발생하면 중복이 생긴 것이므로 제거해야 합니다.

**문서 경계를 넘는 단일 출처**

이 규칙은 PRD 내부뿐 아니라 **AI 프롬프트를 포함한 모든 산출물에 적용됩니다.** 프롬프트에 목록을 하드코딩하지 않고 생성 시점에 본 표를 주입합니다.

v1.0에서 `heading-hierarchy`가 추가되었을 때 프롬프트의 사본이 갱신되지 않아 한 버전 만에 불일치가 발생했습니다. 사본이 존재하는 한 같은 사고가 반복됩니다.

**구현 요건 — 단일 상수에서 파생**

본 문서는 마크다운이므로 코드가 직접 읽을 수 없습니다. 실제 주입 문자열은 코드 내 상수가 됩니다. 이때 **주입 텍스트와 스키마 검증용 열거형을 별도로 정의하면 중복이 문서에서 코드로 자리만 옮긴 것이 됩니다.**

두 산출물은 하나의 상수에서 파생되어야 합니다.

```
조건 유형 상수 (단일 정의)
├─ 프롬프트 주입 텍스트 생성
└─ 스키마 검증 열거형 생성
```

이렇게 하면 "프롬프트가 제시한 유형"과 "검증이 통과시키는 유형"이 구조적으로 어긋날 수 없으며, 일치 여부를 사람이 확인할 필요가 없습니다. 본 표는 그 상수가 구현해야 할 명세로 남습니다.

**파라미터 검증**

각 유형이 요구하는 파라미터가 누락되거나 형식이 맞지 않으면 해당 조건을 거부합니다. 예를 들어 `layout-result`에 기대 배치 값이 없으면 판정이 불가능하므로 유입시키지 않습니다.

**거부 시 처리**

- 조건을 폐기하고 로그를 남깁니다
- 필수 조건이 하나도 남지 않은 구역은 재생성을 요청합니다
- 거부 빈도는 프롬프트 품질 측정에 활용합니다

**`desc` 분리가 덮지 못하는 범위**

판정 로직 고정은 **검사 방식**을 AI 출력에서 분리한 것이며, 다음 두 경로는 여전히 AI 출력에 의존합니다.

| 경로 | 내용 | 대응 |
|---|---|---|
| 학습자에게 보이는 문구 | `desc`가 실제 판정과 어긋나면 학습자는 무엇을 고쳐야 할지 알 수 없음 | 실패 문구를 `type`별 고정 템플릿 + 파라미터로 생성 (F-07-07) |
| 기대값 | `layout-result`의 기대 배치, `list-grouping`의 반복 개수 등은 AI가 생성하고 코드가 신뢰함 | 8.2 검증으로 포착 |

**기대값 오류의 성격:** AI가 3열 2행을 2열 3행으로 잘못 읽으면, 고정 코드는 그 잘못된 기대값을 충실히 판정합니다. 검사 로직이 정확해도 결과는 틀립니다. 이 경로는 판정 계층에서 차단할 수 없으며 8.2 검증에서 포착해야 합니다.

**다중 해석 허용 — 격자 구조 대응**

8.3 재현성 검증에서 동일 시안을 3회 분석한 결과, 2차원 격자 구조에 대해 서로 다른 해석이 나왔습니다.

| 해석 | `list-grouping` 반복 수 | 구조 |
|---|---|---|
| A | 6 | 타일 6개의 평면 나열 |
| B | 3 | 행 3개, 각 행에 타일 2개 |

**두 해석 모두 타당하며, 시안 이미지에는 어느 쪽인지 판별할 정보가 없습니다.** 프롬프트를 개선해도 해소되지 않습니다. 사람이 보아도 갈리는 판단이기 때문입니다.

문제는 어느 해석이 저장되었는지에 따라 **동일한 코드가 정반대로 판정된다**는 점입니다.

| 학습자 코드 | 해석 A 기준 | 해석 B 기준 |
|---|---|---|
| 타일 6개를 하나의 목록에 나열 | 통과 | 실패 |
| 행 단위로 묶고 각 행에 타일 배치 | 실패 | 통과 |

**대응: 파라미터를 단일값이 아닌 허용 집합으로 정의합니다.**

둘 다 올바른 구현이라면 둘 다 통과시켜야 합니다. 하나를 선택하는 것은 4.6.1의 기본 원칙(오탐 방지)에 반합니다.

```json
{
  "type": "list-grouping",
  "target": "제품 타일",
  "accept": [
    { "groupCount": 1, "itemsPerGroup": 6 },
    { "groupCount": 3, "itemsPerGroup": 2 }
  ]
}
```

```json
{
  "type": "layout-result",
  "target": "제품 타일",
  "accept": [
    { "columns": 2, "rows": 3 }
  ]
}
```

`layout-result`의 `accept`는 항상 1개입니다. 말단 요소의 기하 정보로만 기술합니다.

**판정 규칙:** `accept` 배열 중 **하나라도** 만족하면 통과입니다.

**적용 대상은 `list-grouping` 뿐입니다**

| type | `accept` 다중 항목 | 사유 |
|---|---|---|
| `list-grouping` | **허용** | 렌더 결과가 같아도 DOM 그룹 단위가 실제로 다르며, 시안으로 판별 불가 |
| `layout-result` | **불허 (항상 1개)** | 아래 참조 |
| 그 외 5개 유형 | 불허 | 파라미터가 없거나 대상 식별만 필요 |

**`layout-result`에 다중 해석을 두지 않는 이유**

중첩 배치와 평면 배치는 렌더된 말단 요소의 좌표가 동일합니다. 이는 Flex/Grid 선택과 같은 층위의 구현 차이이며, 4.6.5의 렌더 결과 판정이 이미 흡수하도록 설계되어 있습니다.

8.3 재현성 검증에서 3회차가 `1열 3행 + 행 내부 2열`을 낸 것은 해석이 갈린 것이 아니라 **DOM 중첩 구조를 배치 조건에 기술한 것**이며, 4.6.3의 기존 규칙("배치 조건은 결과로 기술, 구현 방식 금지") 위반입니다. 새로운 기능이 아니라 기존 규칙의 준수로 해결됩니다.

따라서 `layout-result`의 기대값은 **말단 요소의 기하 정보로만 기술합니다.**

| 잘못됨 | 올바름 |
|---|---|
| `1열 3행 + 행 내부 2열` | `{ columns: 2, rows: 3 }` |

`accept`를 열어두면 미탐 표면만 넓어집니다.

**문서 전체 범위 조건의 구역별 모드 적용**

`heading-single`과 `heading-order`는 문서 전체를 대상으로 하는 조건입니다. 구역별 모드에서는 학습자가 한 구역만 작성하므로 적용 방식을 정의해야 합니다.

| 조건 | 범위 | 구역 단독 판정 시 문제 |
|---|---|---|
| `heading-single` | 문서 내 `h1` 1개 | 헤더 외 구역에는 `h1`이 없는 것이 정상인데 오탐 발생 |
| `heading-order` | 제목 레벨 건너뜀 없음 | 앞 구역의 제목 레벨을 모르면 판단 불가 |

**채택: 이전 구역들의 확정 HTML을 이어붙여 문서 전체로 판정합니다.**

판정 시점에 통과 완료된 구역들의 HTML과 현재 작성 중인 구역의 HTML을 순서대로 결합하여 하나의 문서를 구성한 뒤 검사합니다. 첫 구역 작성 시에는 앞선 코드가 없으므로 자연스럽게 해당 구역만 검사 대상이 됩니다.

**결합 범위 (엄격히 한정)**

| 항목 | 결합 여부 |
|---|---|
| HTML | 결합 |
| **CSS** | **결합하지 않음** |
| 적용 조건 | **`heading-single`, `heading-order` 두 유형에만 적용** |
| 그 외 모든 조건 | 현재 구역 문서로 판정 |

**CSS를 결합하지 않는 이유**

구역별로 작성하므로 클래스 이름이 겹치는 것은 자연스러우며, 클래스 네이밍은 자유 등급(4.6.2)이라 판정 대상이 아닙니다. 결합 시 구역 4의 `.card { display: block }`이 구역 2의 동명 요소를 덮어써, 학습자가 잘못한 것이 없는데 판정이 틀어집니다.

결합이 필요한 두 유형은 DOM 구조만 보므로 CSS가 필요하지 않습니다.

**`layout-result`를 결합 문서로 판정하지 않는 이유**

3열 미리보기는 현재 구역만 렌더링합니다. 결합 문서에서 배치를 측정하면 학습자가 화면에서 보는 것과 판정 근거가 달라지며, **실패 원인을 화면에서 확인할 수 없어 학습이 성립하지 않습니다.** F-07-07(실패 문구와 실제 판정의 일치)과 동일한 이유입니다.

`heading-single`과 `heading-order`는 애초에 "문서 전체"가 조건의 근거이므로, 현재 구역 화면에 보이지 않는 것을 근거로 판정해도 학습자가 납득할 수 있는 종류입니다.

**다른 방안을 택하지 않은 이유**

| 방안 | 배제 사유 |
|---|---|
| 두 유형을 통짜 모드 전용으로 한정 | 제목 계층은 시맨틱 훈련의 핵심이므로 구역별 모드에서 제외하면 손실이 큼 |
| 구역 단위로 범위 재해석 (구역 내 최상위 제목 1개) | `heading-single`의 의미가 왜곡됨. 구역마다 `h1`이 하나씩 있어도 된다는 잘못된 학습이 발생 |

**부수 요구사항 — 선행 구역 변경 시 재검증**

완료 구역 재진입(F-08-03)이 허용되므로, 앞 구역의 제목 구조를 변경하면 이후 구역의 판정 결과가 달라질 수 있습니다. 예를 들어 헤더의 `h1`을 `h2`로 바꾸면 이후 구역들이 `heading-single`을 위반하게 됩니다.

**처리: 통과 상태를 유지하고 "재확인 필요" 표시만 남깁니다.**

| 항목 | 처리 |
|---|---|
| 통과 상태 | 유지 |
| 후속 구역 개방 | 유지 (잠그지 않음) |
| 시도 횟수 | 차감하지 않음 |
| 표시 | 해당 구역에 재확인 필요 표시, 원인 구역 안내 |

**통과 취소를 택하지 않은 이유**

실패 원인이 해당 구역이 아니라 다른 구역의 변경입니다. 구역 5를 작성 중인 학습자가 구역 1을 수정했다고 구역 2~4가 잠기면 진행이 통째로 되돌아가며, 실질적으로 "완료 구역을 재진입하지 말라"는 신호가 되어 F-08-03을 무력화합니다.

진행을 막기보다 어디를 손봐야 하는지 알려주는 편이 학습 흐름에 맞습니다.

**`accept` 항목의 제약**

`accept` 항목이 늘어날수록 조건은 약해지므로 무제한 허용하지 않습니다.

- `accept`의 모든 항목은 **동일한 시각적 결과를 낳는 구현**이어야 합니다
- 시각적 결과가 다른 해석을 나열하는 것은 조건 무력화이며 거부 대상입니다

**AI 프롬프트 요구사항:** 2차원 격자 구조에서 `list-grouping`의 그룹 단위가 갈릴 때만 `accept`에 복수 항목을 나열합니다. `layout-result`는 항상 1개입니다.

#### 4.6.5 판정 방식

| 대상 | 방식 |
|---|---|
| 시맨틱 | DOM 구조를 역할 기준으로 정규화한 뒤 조건 충족 검사 |
| 레이아웃 | **렌더링 결과 측정** — `getBoundingClientRect()`, `getComputedStyle()`로 실제 계산된 위치·크기 비교 |

레이아웃을 렌더 결과로 판정하므로 Flex·Grid·float 등 구현 방식의 차이는 자동으로 해소됩니다. 결과가 조건을 만족하면 통과입니다.

**측정 통로 — 확정 (검증 완료)**

`sandbox` 속성의 `allow-same-origin`과 `allow-scripts`는 독립된 플래그입니다. `allow-same-origin` 단독 부여 시 부모 문서에서 `contentDocument` 접근이 가능해지지만, `allow-scripts`가 없으므로 문서 내 어떤 스크립트도 실행되지 않습니다.

따라서 **측정 스크립트를 주입할 필요 없이** 부모가 직접 `getBoundingClientRect()`와 `getComputedStyle()`을 호출합니다. "주입 스크립트만 실행하고 사용자 스크립트는 차단"이라는 쟁점 자체가 발생하지 않습니다.

| 구성 | `contentDocument` | 사용자 스크립트 |
|---|---|---|
| `sandbox=""` | 접근 불가 | 차단 |
| `sandbox="allow-same-origin"` | **접근 가능** | **차단** |
| `sandbox="allow-scripts"` + CSP nonce | 접근 불가 (`postMessage` 필요) | 차단 |

**위험한 것은 `allow-scripts`와 `allow-same-origin`의 동시 부여이며, `allow-same-origin` 단독 부여가 아닙니다.**

**검증된 차단 경로**

- 인라인 `<script>`
- `<img onerror>`
- `javascript:` URL (`click()` 호출까지 확인)
- 중첩 iframe으로 권한 확대 시도 — 샌드박스 플래그는 상속되며 자식이 넓힐 수 없음

CSP `script-src 'none'`을 문서에 함께 주입합니다. 측정값에 영향이 없고, 향후 누군가 `allow-scripts`를 실수로 추가해도 스크립트가 실행되지 않는 이중 차단이 됩니다.

**`allow-scripts` + CSP nonce 방식을 택하지 않은 이유**

동작은 하나 두 가지가 불리합니다. 첫째, 주입 스크립트가 파싱 중 실행되어 레이아웃 확정 전에 측정하는 문제가 있으며(실측 시 `width: 0`), 이를 해결하려면 부모가 측정을 요청하고 회신을 기다리는 왕복 구조가 필요합니다. 둘째, nonce 유출 시 사용자 스크립트에 부착될 여지가 있어 검증 부담이 늘어납니다.

**판정 전용 iframe 분리**

미리보기 iframe과 판정용 iframe을 분리합니다. 격리 수준이 아니라 **측정값의 결정성** 때문입니다.

3열 미리보기는 사용자가 경계선을 드래그해 너비를 변경합니다. 그 상태에서 측정하면 "카드 3개가 가로 한 줄"과 같은 조건이 열 너비에 따라 통과와 실패를 오갑니다. 판정은 결정적이어야 하므로 시안 너비에 맞춘 고정 폭에서 측정해야 합니다.

| iframe | sandbox | 용도 |
|---|---|---|
| 미리보기 (3열, 가시) | `""` | 학습자가 보는 화면. 격리 최대 |
| 판정용 (숨김, 고정 폭) | `allow-same-origin` + CSP | 확인 버튼 클릭 시에만 생성, 측정 후 파기 |

완화된 오리진을 갖는 문서의 수명이 판정 순간으로 제한되며, 1단계 구현의 미리보기는 변경하지 않습니다.

#### 4.6.6 회색지대 처리

`<ul><li>` 대 `<div><article>` 처럼 양쪽 모두 타당한 경우는 **필수에서 제외하고 권장으로 배치**합니다. 통과시키되 대안을 안내하는 방식이 학습 도구로서 더 적절합니다.

**F-07-07 상세 — 실패 문구 생성**

판정은 `type`별 고정 코드가 수행하므로(4.6.4), 학습자에게 표시할 실패 문구도 동일한 출처에서 생성해야 합니다. AI가 작성한 `desc`를 그대로 표시하면 실제 판정 내용과 어긋날 수 있습니다.

**어긋난 경우의 문제**

`heading-order`로 판정되어 `h1` → `h3` 건너뜀이 걸렸는데, 화면에 "제품명이 구역 제목보다 하위 계층일 것"이라고 표시되면 학습자는 무엇을 고쳐야 할지 알 수 없습니다. 판정이 정확해도 학습이 성립하지 않습니다.

| 요소 | 역할 |
|---|---|
| 고정 템플릿 + 파라미터 | 실패 문구의 주 출처 |
| `desc` | 조건 목록 표시 등 보조 용도 |
| `hints` | 회차별 힌트. 판정 결과와 별개 |

| 대상 | 복사 기능 | 사유 |

| 사용자 작성 코드 | 제공 가능 | 본인 결과물의 외부 활용을 제한할 이유 없음 |

브라우저 기본 텍스트 선택으로 복사하는 것은 차단하지 않습니다. 본 정책은 기술적 차단이 아니라 **기본 동선 설계**에 관한 것입니다.

**F-07-01 상세 — 회차별 피드백 수위**

| 소진 후 | 모범 예시 공개 | 전체 코드 표시 |

시도 횟수를 1~2회로 설정한 경우 수위 단계를 압축 적용합니다.

```json
  "order": 3,
  "bounds": { "topRatio": 0.21, "heightRatio": 0.18 },
  "sameStructureAs": null,
  "structure": { },
  "rubric": [ ],
  "example": { "html": "", "css": "" }
}
```

| 필드 | 비고 |
|---|---|
| `bounds` | **비율로 저장합니다.** 업로드 이미지의 크기가 제각각이므로 픽셀값은 사용할 수 없습니다 |
| `sameStructureAs` | 동일 구조 반복 구역 표시 (F-02-09) |
| `structure` | 1단계 분석의 의미 구조 트리. 격자는 평면으로 저장 |
| `example` | 3단계에서 생성된 모범 예시. 시도 소진 시 공개 (F-07-02) |

### 6.3 판정 조건

AI 분석 2단계의 출력 형식이며, 본 절이 출처입니다.

```json
{
  "id": "r1",
  "level": "required",
  "type": "list-grouping",
  "target": "제품 타일",
  "accept": [
    { "groupCount": 1, "itemsPerGroup": 6 },
    { "groupCount": 3, "itemsPerGroup": 2 }
  ],
  "desc": "반복되는 제품 타일 6개를 목록으로 묶을 것",
  "hints": {
    "1": "제품 영역의 구조를 다시 확인해보세요.",
    "2": "타일이 같은 구조로 반복되고 있습니다.",
    "3": "반복되는 항목은 목록 요소로 묶습니다."
  }
}
```

| 필드 | 규칙 |
|---|---|
| `type` | 4.6.4의 열거형. 스키마 검증 대상 |
| `accept` | 파라미터 배열. 하나라도 만족하면 통과. `layout-result`는 항상 1개 (F-02-14) |
| `desc` | **표시용. 판정에 관여하지 않음** (4.6.4) |
| `hints` | **조건마다 1세트.** 회차별 수위 3단계 (F-07-01) |

**`hints`가 조건 단위인 이유:** 구역당 하나면 어떤 조건이 실패했는지에 따라 힌트를 선택할 수 없습니다.

**`desc`가 판정에 관여하지 않으므로**, 학습자에게 표시할 실패 문구는 `type`별 고정 템플릿과 `accept` 파라미터로 생성합니다(F-07-07).

`level`이 `recommended`인 항목은 `type`이 `semantic-suggestion`이며 `accept`와 `hints`를 갖지 않습니다.

### 6.4 진행 상태

**구역별 코드를 개별 보관합니다.** F-08-05의 결합 판정과 F-08-03의 완료 구역 재진입이 모두 이 구조를 전제합니다.

```json
{
  "currentSection": "sec-03",
  "sections": {
    "sec-01": {
      "status": "passed",
      "attemptsUsed": 1,
      "code": { "html": "<header>...</header>", "css": "header { ... }" },
      "needsRecheck": false,
      "recheckCause": null
    },
    "sec-02": {
      "status": "passed",
      "attemptsUsed": 2,
      "code": { "html": "...", "css": "..." },
      "needsRecheck": true,
      "recheckCause": "sec-01"
    },
    "sec-03": {
      "status": "in_progress",
      "attemptsUsed": 0,
      "code": { "html": "", "css": "" },
      "needsRecheck": false,
      "recheckCause": null
    }
  }
}
```

| 필드 | 값 |
|---|---|
| `status` | `locked` / `in_progress` / `passed` / `revealed` |
| `attemptsUsed` | 소진 시 `example` 공개 |
| `code` | 구역별 작성 코드. 자동 저장 (F-04-10) |
| `needsRecheck` | 선행 구역 변경으로 재검증 필요 (F-08-06) |
| `recheckCause` | 원인 구역 id. 학습자에게 안내 |

`status`가 `revealed`는 시도를 소진해 모범 예시가 공개된 상태입니다. 통과와 구분해 기록합니다.

**`needsRecheck`가 `true`여도 `status`는 `passed`를 유지하며 후속 구역을 잠그지 않습니다**(F-08-06). 실패 원인이 해당 구역이 아니기 때문입니다.

### 6.5 결합 판정 입력

`heading-single`과 `heading-order` 판정 시에만 구성합니다(F-08-05).

```
결합 대상 = 아래 구역들을 order 순으로 정렬해 이어붙인 HTML

  status = passed    → 해당 구역의 code.html
  status = revealed  → 해당 구역의 example.html   ← 학습자 코드가 아님
  현재 구역          → 작성 중인 code.html
```

**현재 구역은 자기 `order` 자리에 들어갑니다.** 맨 뒤에 붙이지 않습니다.

F-08-03으로 완료 구역에 재진입하면 현재 구역이 마지막이 아닙니다. 구역 2로 돌아간 경우 `[1, 3, 4, 5] + [2]` 순서로 결합하면 `heading-order`가 문서 순서대로 제목 레벨을 검사하므로 정상 코드가 건너뜀으로 잡힙니다.

**현재 구역보다 뒤에 있는 통과 구역도 포함합니다.** 구역 4에 `h1`이 있는데 구역 2를 다시 작성 중이라면, 구역 4를 제외할 경우 구역 2가 `h1`을 가져야 통과하게 되어 잘못된 학습을 유도합니다.

**`revealed` 구역은 `example.html`을 사용합니다**

`revealed`는 시도를 소진해 예시가 공개된 상태이며, **정의상 판정을 통과하지 못한 구역입니다.** 학습자 코드를 결합하면 그 구역의 위반이 이후 모든 구역으로 전파됩니다.

예를 들어 구역 1에서 `h1`을 둘 작성한 채 소진하면, 이후 모든 구역의 결합 문서에 `h1`이 둘 이상 포함되어 **구역 2를 어떻게 작성해도 `heading-single`을 통과할 수 없습니다.** 학습자는 자기 코드에 문제가 없는데 계속 실패하며, 힌트는 현재 구역 조건만 다루므로 원인을 알 수 없습니다.

예시가 이미 공개된 구역이므로 학습자도 해당 코드를 확인한 상태이며, 문서가 항상 올바른 기준선에서 이어집니다.

**요구사항:** 판정 근거에 학습자가 작성하지 않은 코드가 포함되므로, 해당 구역이 예시 코드로 대체되었음을 화면에 명시합니다(F-08-08).

| 항목 | 처리 |
|---|---|
| HTML | 결합 |
| **CSS** | **결합하지 않음** (F-08-07) |
| 적용 조건 | `heading-single`, `heading-order` 두 유형만 |
| 그 외 조건 | 현재 구역 문서로 판정 |

### 6.6 통짜 모드

`settings.mode`가 `whole`인 경우 `sections`는 항목 하나만 가지며, 그 구역이 시안 전체를 범위로 합니다. 결합 판정(6.5)은 불필요하며 조건 판정이 모두 단일 문서에서 수행됩니다.

### 7.2 CodeMirror 6 선택 사유

F-04-07(이름 제안 토글)이 자동완성을 항목별로 분리 제어할 것을 요구합니다. CodeMirror 6는 `autocompletion()` 확장에 완성 소스를 개별 지정하는 구조이므로 다음 분리가 가능합니다.

| 기능 | 출처 | 제어 |
|---|---|---|
| 태그 이름 제안 | `autocompletion()` | 토글 대상 |
| HTML 속성 이름·값 제안 | `autocompletion()` | 토글 대상 |
| CSS 속성명 제안 | `autocompletion()` | 토글 대상 |
| CSS 값 제안 | `autocompletion()` | 토글 대상 |
| 닫는 태그 자동 생성 | `html({ autoCloseTags })` | 항상 활성 |
| 괄호·따옴표 짝맞춤 | `closeBrackets()` | 항상 활성 |

**제어 방식**

토글 대상은 전부 `autocompletion()`에서 발생하고, 항상 활성 대상은 별개 확장입니다. 따라서 완성 소스를 개별 필터링(`override`)하지 않고 **`autocompletion()` 확장 자체를 Compartment로 넣고 빼는 방식**을 사용합니다. 언어 패키지가 등록하는 완성 소스의 내부 표현에 의존하지 않으므로 라이브러리 버전 변경에 안정적입니다.

**HTML 속성 제안 포함 사유**

`class`, `alt`, `aria-label` 등 속성 이름 역시 학습자가 직접 떠올려야 할 대상이며, 특히 접근성 속성을 자동 제시하는 것은 시맨틱 훈련을 저해합니다. 태그 제안과 동일하게 토글 대상에 포함합니다.

Monaco Editor는 IDE 지향으로 번들 크기가 크고 완성 항목 분리가 상대적으로 복잡합니다.

### 8.1 AI 분석 정확도 — 1차 검증 완료

**검증 방법:** 실제 운영 중인 웹사이트 4종(패스트캠퍼스 강의 상세, HOOT UP, JW Anderson, Apple 대한민국)의 데스크톱 전체 스크린샷을 AI에 제공하고 구역 분할·의미 구조·배치 관계 추출을 시행.

**결과:** 구역 분할, 반복 항목 인식, 배치 관계 파악 모두 실사용 가능한 수준으로 확인. 이미지만으로 학습 목표(시맨틱·레이아웃) 달성에 필요한 정보는 충분히 추출됨.

**부수 발견**

| 발견 | 대응 |
|---|---|
| 동일 구조 구역이 반복되는 페이지 존재 (HOOT UP 4·5·6, Apple 프로모션 유닛) | 분석 산출물에 반복 구조 표시 항목 추가 검토 |

| 동일 의미 구조가 서로 다른 배치로 등장 (Apple: 전체 너비 1개 / 2열 6개) | 학습 소재로 유효. 시맨틱과 레이아웃 분리 사고 훈련에 적합 |

### 8.2 판정 정확도 — 미검증

**오탐과 미탐을 모두 측정해야 합니다.** 오탐만 측정하는 설계로는 F-05-04에서 발견된 유형(모든 측정값이 0이 되어 무조건 통과)을 잡아낼 수 없습니다.

| 측정 대상 | 방법 | 실패의 성격 |
|---|---|---|
| 오탐률 | 동일 시안에 대해 서로 다른 방식으로 작성한 복수의 정답 코드를 통과시킴 | 학습자가 항의하므로 발견됨 |
| 미탐률 | 조건을 의도적으로 위반한 코드가 실제로 걸리는지 확인 | **조용히 통과하므로 발견되지 않음** |

미탐은 학습자가 잘못된 코드를 정답으로 인식하게 만들므로, 학습 도구에서는 오탐보다 위험합니다.

**검증용 정답 코드는 반드시 시안만 보고 작성합니다**

조건 목록을 참고해 코드를 작성하면 AI가 생성한 기대값에 맞춰 쓰게 되어, 기대값 자체가 틀린 경우(3열 2행을 2열 3행으로 잘못 읽는 등)를 포착할 수 없습니다. 검증이 스스로를 검증하는 구조가 됩니다.

**기대값 오류는 판정 계층에서 차단할 수 없으며(4.6.4), 본 검증이 유일한 포착 경로입니다.**

**미탐 검증 항목 예시**

- 카드를 세로로 쌓아놓고 가로 배치 조건을 통과하는지
- 반복 항목을 목록으로 묶지 않고 `list-grouping` 조건을 통과하는지
- `alt` 없는 이미지가 `image-alt` 조건을 통과하는지
- 제목 계층을 건너뛰고 `heading-order` 조건을 통과하는지
- `accept` 항목이 과도하게 넓어 위반 코드가 통과하는지

### 8.3 조건 생성 품질 — 1차 검증 완료

**8.1 검증 결과, 본 도구의 주된 위험은 AI가 구조를 읽지 못하는 것이 아니라 판단이 갈리는 사항을 필수 조건으로 잡는 것으로 확인되었습니다.**

Apple 페이지의 2열 3행 타일 영역은 "그리드 하나"와 "2열 행 3개의 수직 배열" 양쪽으로 해석 가능하며, 마크업이 전혀 달라집니다. 이런 사항이 필수 조건이 되면 오탐이 확정적으로 발생합니다.

**대응:** 4.6.3의 화이트리스트 정책을 도입하고, 4.6.4의 목록·스키마 검증·판정 로직 고정으로 이를 강제합니다.

**1차 검증 결과 (Apple 제품 타일 구역, 프롬프트 v1)**

| 확인 항목 | 결과 |
|---|---|
| 필수 조건이 화이트리스트 내에 있는가 | 통과 |
| `layout-result`에 CSS 속성명이 없는가 | 통과 — "가로 2개씩 3행으로 놓일 것" |
| 그리드/플렉스 판단이 필수로 올라왔는가 | 발생하지 않음 |
| 링크/버튼 판단이 권장에 머물렀는가 | 통과 |
| `article`/`div` 판단이 권장에 머물렀는가 | 통과 |

**발견된 문제 — 유형 오용**

`type`은 유효하나 `desc`가 해당 유형의 정의와 다른 조건을 기술하는 사례가 확인되었습니다.

```json
{ "type": "heading-order", "desc": "제품명이 구역 제목보다 하위 계층일 것" }
```

`heading-order`는 계층 건너뜀을 검사하는 유형이나, 위 조건은 상하 관계라는 별개의 검사입니다. **스키마 검증은 `type` 값만 보므로 이를 통과합니다.**

**대응 완료**

- 판정 로직을 `type`별 고정 코드로 정의하고 `desc`는 판정에 관여하지 않도록 함 (4.6.4)
- 조건 자체는 타당하므로 `heading-hierarchy`를 화이트리스트에 정식 추가 (7개 유형)

**잔여 검증 항목**

- AI가 화이트리스트를 벗어나는 빈도 (차단은 4.6.4가 담당하므로 프롬프트 품질 측정용 참고 지표)
- 동일 시안 3회 분석 시 재현성 — 아래 기준 참조
- 3단계에서 생성된 모범 예시가 2단계 조건을 실제로 만족하는지

**재현성 비교 단위: `(type, 파라미터)` 집합**

조건의 개수와 유형만 비교해서는 안 됩니다. 판정 결과를 좌우하는 것은 유형과 파라미터의 조합이기 때문입니다.

| 사례 | 유형 기준 | 실제 |
|---|---|---|
| 3회 모두 `layout-result` 1개, 기대 배치가 "2열 3행 / 2열 3행 / 3열 2행" | 재현 성공 | **실패 — 판정이 뒤집힘** |
| 3회의 `desc` 문구가 모두 다르나 `(type, 파라미터)`는 동일 | 실패 | **성공 — 판정 동일** |

`desc`는 판정에 관여하지 않으므로(4.6.4) 문구 차이는 재현성 실패로 집계하지 않습니다.

**부수 효과 — 기대값 오류 탐지**

3회 분석의 파라미터가 갈리면 최소 2회는 틀린 것이므로, 시안과 대조하기 전에 의심 지점을 좁힐 수 있습니다. 다만 **3회가 일치해도 정확성이 보장되지는 않습니다.** 동일한 방식으로 세 번 오독하는 경우가 가능하므로 8.2 검증은 여전히 필요합니다.

**재현성 검증 결과 (Apple 제품 타일 구역, 3회)**

| 회차 | 조건 구성 |
|---|---|
| 1 | `list-grouping`(반복 6) · `layout-result`(2열 3행) · `image-alt` · `heading-hierarchy` |
| 2 | `list-grouping`(반복 6) · `layout-result`(2열 3행) · `image-alt` |
| 3 | `list-grouping`(그룹 3개, 각 2개) · `layout-result`(1열 3행 + 행 내부 2열) · `image-alt` |

**판정: 재현성 실패.** 두 종류의 불일치가 확인되었습니다.

| 불일치 | 내용 | 영향 |
|---|---|---|
| 조건 개수 | `heading-hierarchy`가 1회차에만 생성됨 | 통과 기준이 회차마다 달라짐 |
| 구조 해석 | 3회차가 격자를 행 단위로 해석 | **동일 코드가 정반대로 판정됨** |

**추가 분석 — 원인이 1단계에 있었을 가능성**

3회차에서 `list-grouping`(그룹 3개)와 `layout-result`(행 계층 포함)가 **함께** 나타났습니다. 2단계가 독립적으로 두 번 오판했다기보다, **1단계 구조 트리에 이미 행 계층이 포함되어 있었다고 보는 편이 자연스럽습니다.**

이 경우 2단계의 `accept` 다중 해석은 무력합니다. 받은 트리에 행 계층이 있으면 평면 해석이 존재한다는 것을 알 수 없어 나열할 재료가 없습니다.

**대응:** 1단계 프롬프트에 격자 구조를 평면으로 세도록 지시를 추가했습니다(프롬프트 v6). 모호성이 1단계에서 확정되지 않고 2단계로 내려가야 `accept`가 기능합니다.

**주의:** v5 재검증에서 재현성이 개선된 것은 `accept` 도입의 효과가 아니라 1단계가 3회 모두 평면으로 읽은 결과일 수 있습니다. 프롬프트 v6 적용 후 재측정이 필요합니다.

**대응 — 원인이 둘로 나뉩니다**

`list-grouping`의 그룹 단위 차이는 진짜 해석 불일치입니다. 렌더 결과가 같아도 DOM 구조가 실제로 다르고 시안으로 판별할 수 없으므로, 4.6.4의 다중 해석 허용(`accept` 배열)으로 대응합니다.

`layout-result`의 차이는 해석 불일치가 아닙니다. `1열 3행 + 행 내부 2열`은 DOM 중첩 구조를 배치 조건에 기술한 것으로, 4.6.3의 기존 규칙 위반입니다. 기대값을 말단 요소의 기하로만 기술하도록 강제하면 해소되며, 다중 해석은 필요하지 않습니다.

조건 개수 불일치는 별도 사안입니다. `heading-hierarchy`가 누락되면 검사가 하나 줄어들 뿐 잘못된 판정을 내리지는 않으므로, 미탐 방향의 손실로 분류하고 8.2에서 측정합니다.

### 8.4 레이아웃 측정 통로 — 해결 완료

**결론: 4.6.5의 레이아웃 판정 방식은 재설계가 불필요합니다.** 조건 유형 `layout-result`를 그대로 사용합니다.

`allow-same-origin`과 `allow-scripts`가 독립 플래그라는 점을 이용해, `allow-same-origin` 단독 부여로 측정 통로를 확보하면서 스크립트는 전면 차단합니다. 측정 스크립트 주입이 불필요하므로 당초 우려했던 쟁점(주입 스크립트만 선별 실행)이 발생하지 않습니다.

판정용 iframe은 미리보기와 분리하여 고정 폭으로 운영합니다. 측정값의 결정성 확보가 목적입니다.

상세 설계와 검증 결과는 4.6.5를 참조하십시오.
