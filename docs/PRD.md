## 1. 개요

### 1.1 한 줄 정의

사용자가 등록한 웹 디자인 시안을 AI가 분석하고, 사용자가 직접 HTML/CSS를 작성해 시맨틱 마크업과 레이아웃 구현 능력을 훈련하는 웹 기반 학습 도구.

### 1.2 배경

HTML/CSS 학습에서 문법은 자료가 충분하지만, "이 화면을 어떤 구조로 마크업할 것인가"에 대한 판단력은 실전 반복 없이는 길러지지 않습니다. 기존 코딩 챌린지 플랫폼은 정해진 시안만 제공하므로 학습자가 원하는 디자인으로 연습할 수 없고, 피드백도 커뮤니티 리뷰에 의존해 즉시성이 떨어집니다.

본 도구는 **사용자가 원하는 시안을 직접 등록**하고 **즉시 구조적 피드백**을 받는 환경을 목표로 합니다.

### 1.3 학습 목표 (Scope의 기준)

본 도구가 훈련시키는 대상은 다음 두 가지로 한정합니다.

1. **시맨틱 마크업** — 콘텐츠의 의미에 맞는 HTML 요소 선택, 문서 구조의 논리적 계층 구성
2. **레이아웃 구현** — 시안의 배치 관계를 CSS로 재현하는 능력

### 1.4 비목표 (Non-goals)

다음은 **의도적으로 다루지 않습니다.**

| 항목 | 제외 사유 |
|---|---|
| 픽셀 단위 정확도 | 학습 목표와 무관. 간격 2px 차이는 시맨틱·레이아웃 실력과 관계없음 |
| 폰트 이름 일치 | 시안에서 정확히 판별 불가하며 학습 가치 낮음 |
| 인터랙션 (hover, 애니메이션) | 별도 학습 영역. 향후 확장 후보 |
| JavaScript | 범위 외 |
| 반응형 브레이크포인트 | v1 범위 외. 향후 확장 후보 |
| 코드 스타일 (들여쓰기, 클래스 네이밍) | 판정 대상 아님 |
| **답안에서 요소를 누락한 경우의 검출** | 아래 별도 항목 참조 |
| **세로로 매우 긴 시안 (종횡비 1:5 초과)** | 분석 모델의 이미지 해상도 한계로 글자를 읽지 못함. 계산 근거는 4.1을 참조 |

**답안에서 요소를 누락한 경우의 검출**

필수 조건은 구조 패턴만 기술하며 특정 요소의 존재를 요구하지 않습니다. 이는 `target`을 판정에서 제외한 결정(4.6.4)의 귀결입니다. 결과적으로 학습자가 요소를 아예 빼면 그 요소에 걸린 조건이 공허하게 통과합니다.

| 조건 | 공허하게 통과하는 경우 |
|---|---|
| `form-label` | 답안에 폼 컨트롤이 하나도 없음 — 검사할 대상이 없으므로 통과 |
| `image-alt` | 답안에 이미지가 하나도 없음. 또한 `alt=""`도 통과 (장식 이미지를 오탐하지 않기 위함) |

고치려면 조건이 특정 요소의 존재를 요구할 수 있어야 하고, 그것은 `target`을 판정에 다시 끌어들이는 것입니다. 8.3에서 오탐 0/12를 얻은 근거가 그 결정이었으므로, 되돌리면 오탐이 늘어납니다. **4.6.1의 원칙상 미탐을 감수하는 쪽이 맞습니다** — 틀리지 않은 코드를 틀렸다고 판정하는 것이 가장 큰 실패입니다.

`layout-result`와 `list-grouping`이 반복 항목의 개수와 배치를 요구하므로, 구역의 주요 구조를 통째로 빠뜨리는 것은 여전히 걸립니다. 누락이 통과하는 범위는 조건이 걸리지 않은 개별 요소로 한정됩니다.

## 2. 사용자 정의

### 2.1 주 사용자

- HTML/CSS 문법은 알지만 실제 시안을 보고 구조를 잡는 데 어려움을 겪는 학습자
- 퍼블리싱 입문자 및 전환자
- 시맨틱 태그를 알지만 실무에서 언제 무엇을 쓸지 판단이 서지 않는 사용자

### 2.2 사용 맥락

- 개인 학습용. 다중 사용자 협업·평가 기능은 범위 외
- 반복 연습 도구. 1회성 테스트가 아님

## 3. 핵심 사용자 흐름

```
[1] 소스 등록
     ├─ 이미지 업로드 (PNG/JPG) 또는 Figma 파일·링크
     ├─ 학습 모드 선택 (통짜 / 구역별)
     └─ 시도 횟수 설정 (1~5회)
              ↓
[2] AI 분석 1단계 — 구조 분석 (결과 영구 저장)
     ├─ 의미 구조 트리 추출
     ├─ 배치 관계 추출
     ├─ 최상위 제목 위치 식별
     └─ 구역 분할 (구역별 모드일 때만)
              ↓
[3] 구역 확인 및 조정 (구역별 모드, 별도 화면)
     ├─ 시안 위 오버레이로 AI 분할 결과 확인
     ├─ 병합 / 분할 / 경계 조정 (선택적)
     └─ 구역 확정
              ↓          ※ 통짜 모드는 [3]을 건너뛰고 [2]에서 바로 [4]로 간다.
              ↓             단, 구역이 상한(6.6)을 넘으면 구역별로 전환되어 [3]을 거친다.
[4] AI 분석 2·3단계 — 조건·예시 생성 (확정된 구역 기준)
     ├─ 판정 조건 생성 (필수/권장/자유)  ┐ 구역마다 별도 요청 (4.2 F-02-18)
     └─ 모범 예시 코드 생성              ┘
              ↓
[5] 코딩 + 실시간 미리보기 (반복)
              ↓
[6] 확인 요청 → 판정 → 회차별 피드백
     ├─ 통과 → 다음 구역 또는 완료
     └─ 미통과 → 시도 횟수 차감 → [5]로 복귀
              ↓
[7] 시도 소진 시 모범 예시 공개
```

**중요:** AI 호출은 [2]와 [4]에서만 발생합니다. 학습이 시작된 뒤([5]~[7])에는 저장된 분석 결과로 브라우저 내에서 처리되며 런타임 AI 호출이 없습니다.

**조건 생성을 구역 확정 이후로 두는 이유**

조건은 구역에 묶여 있는데 [3]에서 구역 경계가 바뀝니다. 구역을 분할하면 기존 조건을 어느 쪽으로 보낼지 판단할 근거가 없습니다. `layout-result`의 기대값이 어느 구역의 격자를 가리키는지 조건만으로는 알 수 없고, `target`은 판정에 쓰지 않으므로(4.6.4) 기계적으로 나눌 수 없습니다.

| 처리 방식 | 결과 |
|---|---|
| 양쪽 구역에 조건 복제 | 한쪽은 반드시 실패 — 확정적 오탐 |
| 조건 폐기 | 필수 조건이 없는 구역이 생김 — 무엇을 작성해도 통과, 미탐 |
| 분할된 구역만 재분석 | 2단계는 구조 트리 전체를 입력으로 받으므로 구조도 다시 나눠야 함. 절차만 복잡해지고 비용은 비슷 |

병합도 안전하지 않습니다. 조건을 이어붙이면 검사 범위가 넓어져 `layout-result`의 후보 탐색에 엉뚱한 집합이 걸릴 수 있습니다.

**확정된 구역으로 조건을 만들면 이 문제가 발생하지 않습니다.** 대가는 사용자가 구역 편집을 마친 뒤 한 번 더 대기한다는 점이며, 통짜 모드는 구역 편집이 없으므로 두 호출이 연속으로 이어집니다.

## 4. 기능 요구사항

### 4.1 소스 등록 (F-01)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-01-01 | 이미지 파일 업로드 (PNG, JPG) | 필수 |
| F-01-02 | Figma 파일 또는 링크 등록 | 필수 |
| F-01-03 | 학습 모드 선택 UI (통짜 / 구역별) | 필수 |
| F-01-04 | 시도 횟수 설정 (1~5, 기본값 3) | 필수 |
| F-01-05 | 등록된 소스 목록 관리 (재진입, 삭제) | 필수 |
| F-01-06 | 업로드 소스의 저작권 책임 고지 | 필수 |
| F-01-07 | 종횡비가 상한을 넘는 시안은 등록을 막고 이유를 안내 | 필수 |

**시안 크기 제약 — 종횡비 1:5**

세로가 가로의 5배를 넘는 시안은 등록할 수 없습니다. 두 개의 독립된 제약이 거의 같은 선에서 만나며, 하나의 규칙으로 둘 다 덮입니다.

*제약 ①: API의 하드 한계*

한 변이 8000px를 넘는 이미지는 API가 400으로 거부합니다. 저장 폭이 1600px이므로 세로 8000px가 한계이고, 이는 **종횡비 5.0**에 해당합니다.

*제약 ②: 모델의 이미지 다운샘플*

분석 모델(Claude Opus 5)은 긴 변을 **2576px**로 줄여서 봅니다. 따라서 모델이 실제로 보는 가로 픽셀은 다음과 같습니다.

```
모델이 보는 가로 = 2576 ÷ 종횡비
```

**이 값은 리사이즈로 바꿀 수 없습니다.** 종횡비만의 함수이므로, 원본을 어떤 크기로 줄여 보내든 결과가 같습니다. 본문 글자를 읽으려면 가로 500px 이상이 필요하고, 이는 **종횡비 5.15**에 해당합니다.

*실측*

| 시안 | 종횡비 | 모델이 보는 크기 | 결과 |
|---|---|---|---|
| 패션 브랜드 페이지 (1920×8486) | 1 : 4.4 | 583×2576 | 구역 이름·상품명·버튼 문구까지 정확히 읽음. 구조 트리에 실제 텍스트가 담김 |
| 강의 랜딩 페이지 (1920×27108) | 1 : 14.1 | 183×2576 | **텍스트 주장 0건.** 구역을 색으로 부르고("주황 띠 안내"), 검증한 3개 구역의 이름과 구조가 모두 실제 내용과 불일치 |

두 번째 사례에서 구조 트리에 `text` 필드가 하나도 없었던 것이 결정적 신호입니다. 모델이 읽지 못했다는 사실을 스스로 드러낸 것이며, 없는 텍스트를 지어내지는 않았습니다.

*상한을 5로 정한 이유*

제약 ①이 5.0, 제약 ②가 5.15입니다. 더 엄격한 쪽을 취해 **5**로 정합니다. 이 선을 지키면 API가 거부하지 않고 모델이 보는 가로도 515px 이상이 확보됩니다.

*초과 시 처리*

파일 선택 즉시 종횡비를 재고 초과하면 등록 버튼을 잠급니다. API 호출 전이므로 비용이 발생하지 않습니다. 사용자에게는 페이지를 몇 부분으로 잘라 나눠 등록하도록 안내합니다.

시안을 세로로 잘라 여러 장으로 첨부하면 이 상한을 넘을 수 있으나, 구조 분석이 여러 장을 하나의 페이지로 보고 구역 목록을 내야 하고 타일 경계에 걸친 구역을 처리해야 합니다. v1 범위 외로 둡니다.

### 4.2 AI 분석 (F-02)

호출은 두 시점으로 나뉩니다. **1단계(구조 분석)는 등록 시점에**, **2·3단계(조건·예시 생성)는 구역 확정 이후에** 실행하고 결과를 저장합니다. 학습이 시작된 뒤에는 호출하지 않습니다.

구역별 모드에서 사용자가 구역을 병합하거나 분할할 수 있으므로, 조건을 먼저 만들면 확정된 구역과 어긋납니다. 상세는 3장을 참조하십시오.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F-02-01 | 의미 구조 트리 추출 (요소 역할 식별) | 필수 |
| F-02-02 | 배치 관계 추출 (포함 관계, 형제 방향, 반복 단위) | 필수 |
| F-02-03 | 판정 조건 생성 (필수/권장/자유 3등급 분류) | 필수 |
| F-02-04 | 모범 예시 코드 생성 (HTML/CSS) | 필수 |
| F-02-05 | 구역 분할 (구역별 모드) | 필수 |
| F-02-06 | 참고 정보 추출 (색상, 대략적 간격) | 권장 |
| F-02-07 | 분석 실패 시 재시도 및 오류 안내 | 필수 |
| F-02-08 | 필수 조건은 화이트리스트(4.6.4) 내에서만 생성 | 필수 |
| F-02-11 | AI 출력 저장 전 스키마 검증으로 화이트리스트 강제 (4.6.4) | 필수 |
| F-02-12 | 판정 로직은 `type`에 대응하는 고정 코드가 수행하며 `desc`에 의존하지 않을 것 (4.6.4) | 필수 |
| F-02-13 | `list-grouping`의 그룹 단위가 갈리는 경우 가능한 해석을 모두 `accept`에 나열할 것 (4.6.4) | 필수 |
| F-02-14 | `layout-result`의 기대값은 말단 요소의 기하로만 기술할 것 (4.6.4) | 필수 |
| F-02-15 | 프롬프트 주입 텍스트와 스키마 검증 열거형을 단일 상수에서 파생할 것 (4.6.4) | 필수 |
| F-02-16 | 1단계 분석은 `mainTitleSectionId`를 반환하며, 유효하지 않으면 재생성할 것 (6.1) | 필수 |
| F-02-17 | 조건·예시 생성은 구역 확정 이후에 실행하며 확정된 구역을 입력으로 받을 것 (3장) | 필수 |
| F-02-18 | 조건·예시 생성은 구역 하나씩 별도 요청으로 실행할 것 | 필수 |
| F-02-19 | 통짜 모드는 구조 분석 직후 구역 수를 재고, 상한 초과 시 구역별로 전환할 것 (6.6) | 필수 |
| F-02-09 | 동일 구조 반복 구역 표시 | 권장 |
| F-02-10 | 구역 수 상한 초과 시 경고 | 권장 |

**조건·예시 생성을 구역 단위로 나누는 이유 (F-02-18)**

구역 전체를 한 요청에 담으면 출력량이 구역 수에 비례해 늘어납니다. 11구역 시안에서 한 요청이 **290초**가 걸렸고, 구역이 늘수록 배포 환경의 함수 실행 시간 한도를 넘길 수밖에 없습니다.

구역 단위로 나누면 **한 요청의 시간이 구역 수와 무관해집니다**(실측 약 55초). 전체 소요는 동시 실행 4개 기준 11구역에 161초입니다. 총 시간 단축보다 요청당 시간이 상수가 된 것이 핵심입니다. 부수적으로 캐시가 구역 단위로 걸리고, 실패한 구역만 다시 부를 수 있습니다.

나눠 만들면 각 구역의 예시가 서로의 제목 단계를 알 수 없으므로, 요청마다 **구역 목록과 최상위 제목 구역 여부**를 함께 넘기고 `h1`을 그 구역에만 쓰도록 지시합니다. 11구역 결합 문서에서 `heading-single`·`heading-order` 통과를 확인했습니다.

**의미 구조 트리 예시**

```
페이지
├─ 헤더
│   ├─ 로고 (링크)
│   └─ 주 메뉴 (반복 항목 4개, 가로 배치)
├─ 본문
│   ├─ 페이지 제목 (최상위 제목)
│   └─ 상품 목록 (반복 항목 6개, 가로 3개씩 2행)
│       └─ 상품 카드
│           ├─ 이미지
│           ├─ 상품명 (하위 제목)
│           └─ 가격
└─ 푸터
    └─ 저작권 표시
```

역할 기반으로 기술하며 특정 태그를 지정하지 않습니다. 태그 선택은 사용자의 판단 영역입니다.

**F-05-04 상세 — 숨김 방식 (중요)**

**판정용 iframe을 `display:none`으로 숨겨서는 안 됩니다.**

`display:none`은 레이아웃 박스를 생성하지 않으므로 모든 측정값이 0이 됩니다. 이때 오류는 발생하지 않으며, 모든 요소의 `top`이 0으로 동일해지므로 **배치가 전혀 맞지 않는 코드도 `layout-result` 조건을 전부 통과합니다.**

이는 오탐(정답을 오답 처리)과 반대 방향의 실패이며, 예외 없이 조용히 통과하므로 발견이 어렵습니다. 학습자는 잘못 작성한 코드를 정답으로 인식하게 됩니다.

| 숨김 방식 | 측정값 | 판정 |
|---|---|---|
| `display:none` | 전부 0 | **무조건 통과 (오작동)** |
| `visibility:hidden` | 정상 | 정상 |
| 화면 밖 배치 | 정상 | 정상 |
| 보이는 상태 (대조군) | 정상 | 정상 |

**채택: 화면 밖 배치** (`position:absolute; left:-10000px`)

`visibility:hidden`은 문서 흐름에서 자리를 차지하여 부모 레이아웃에 영향을 줄 수 있으므로 제외합니다.

**F-05-06 상세 — 측정 시점**

사용자 CSS의 배경 이미지나 크기가 지정되지 않은 `<img>`가 있는 경우, 리소스 로드 전후의 측정값이 달라집니다. iframe의 `load` 이벤트는 하위 리소스 로드까지 대기하므로 그 이후에 측정합니다.

웹폰트 로드 완료(`document.fonts.ready`)까지 대기하는 방안도 있으나, 폰트 일치는 비목표(1.4)이므로 적용하지 않습니다.

### 4.6 판정 (F-06)

**본 도구의 핵심이며 가장 높은 실패 위험을 가진 영역입니다.**

#### 4.6.1 기본 원칙

> **모범 예시 코드와 사용자 코드를 직접 비교하지 않습니다.**

동일한 시안에 대해 올바른 구현은 다수 존재합니다. 코드 대조 방식은 정답을 오답으로 판정하는 오류를 필연적으로 발생시킵니다. 따라서 판정은 **조건 목록 충족 여부**로 수행합니다.

#### 4.6.2 조건 3등급

| 등급 | 처리 | 예시 |
|---|---|---|
| **필수** | 미충족 시 지적, 통과 불가 | **4.6.4의 조건 유형 정의표가 유일한 출처입니다.** 이 문서 내 다른 위치에 필수 조건 목록을 중복 기재하지 않습니다 |
| **권장** | 통과시키되 안내 문구 표시 | 메뉴를 `div`로 감쌈 → `nav` 제안, 카드를 `div`로 구성 → `article` 제안 |
| **자유** | 판정하지 않음 | Flex/Grid 선택, 클래스 이름, 구조적으로 등가인 요소 선택, 코드 포맷 |

**설계 원칙: 필수 조건은 최소한으로 잡습니다.** 판단이 애매하면 권장으로, 더 애매하면 자유로 내립니다. 틀리지 않은 코드를 틀렸다고 판정하는 것이 가장 큰 실패입니다.

#### 4.6.3 필수 조건 화이트리스트 — 정책

**AI가 필수 조건을 자유롭게 정하도록 두지 않습니다.** 사전에 정의된 목록 안에서만 선택하게 하고, 목록 밖의 모든 판단은 권장 이하로 배치합니다. 오탐을 구조적으로 차단하기 위한 장치입니다.

**목록의 유일한 출처는 4.6.4의 조건 유형 정의표입니다.** 본 절을 포함해 문서 내 다른 위치에 목록을 중복 기재하지 않습니다. 구현 시 코드의 열거형도 4.6.4를 참조합니다.

**목록 밖 판단의 예시 (전부 권장 이하)**

| 판단 | 사유 |
|---|---|
| `nav` / `section` / `article` / `div` 선택 | 맥락에 따라 복수의 정답 존재 |
| `<ul><li>` 대 `<div><article>` | 양쪽 모두 타당 |
| 링크(`a`)인가 버튼(`button`)인가 | 동작에 따라 다름. 시안만으로 확정 불가 |
| 각주 번호의 `sup` 처리 | 선택 사항 |
| 캐러셀 인디케이터의 시맨틱 | 장식/컨트롤 판단이 갈림 |

**배치 조건의 서술 방식**

배치 조건은 반드시 **결과**로 기술해야 하며 **구현 방식**으로 기술해서는 안 됩니다.

| 잘못된 기술 | 올바른 기술 |
|---|---|
| "그리드로 배치할 것" | "타일 6개가 2열 3행 위치에 놓일 것" |
| "Flex로 가로 정렬할 것" | "카드 3개의 세로 위치가 동일할 것" |

구현 방식을 조건에 넣으면 렌더 결과 판정의 이점이 사라지고 오탐이 발생합니다.

#### 4.6.4 화이트리스트 강제 — 스키마 검증과 판정 로직 고정

**화이트리스트 준수를 프롬프트에만 의존하지 않습니다.** 두 개의 계층으로 강제합니다.

| 계층 | 역할 | 신뢰도 |
|---|---|---|
| 프롬프트 | AI가 올바른 조건을 생성하도록 유도 | 확률적 |
| 스키마 검증 | `type` 값이 열거형에 속하는지 검사 | 결정적 |
| **판정 로직 고정** | **`type`별 검사 내용을 코드로 정의** | **결정적** |

**스키마 검증만으로 불충분한 이유**

스키마 검증은 `type` 값만 확인하며 `desc`가 해당 유형의 정의에 부합하는지는 판단하지 못합니다. 검증 과정에서 실제로 다음 사례가 발견되었습니다.

```json
{ "type": "heading-order", "desc": "제품명이 구역 제목보다 하위 계층일 것" }
```

`heading-order`의 정의는 "제목 계층을 건너뛰지 않을 것"(`h1` → `h3` 금지)이나, 위 조건은 "상하 관계"라는 다른 검사를 기술하고 있습니다. `type` 값이 유효하므로 스키마 검증을 통과합니다.

**대응: `desc`는 판정에 관여하지 않습니다.**

`desc`는 학습자에게 표시할 문구이며, 실제 판정은 `type`에 대응하는 고정된 코드가 수행합니다. AI가 `desc`에 무엇을 쓰든 판정 동작은 변하지 않습니다.

**조건 유형 정의 (화이트리스트 단일 출처)**

| type | 검사 내용 | AI 제공 파라미터 | 생성 주체 | 채택 근거 |
|---|---|---|---|---|
| `heading-order` | 제목 요소의 레벨이 2 이상 건너뛰지 않는지 | 없음 | **엔진 상시** | `h1` → `h3`은 명백한 오류 |
| `heading-single` | 문서 내 `h1`이 정확히 1개인지 | 없음 | **엔진 상시** | 문서 구조의 기본 |
| `image-alt` | 구역 내 모든 의미 있는 이미지에 `alt`가 존재하는지 | 없음 | AI 생성 | 접근성 필수 요건 |
| `list-grouping` | 구역 내에 N개의 동일 구조 항목을 담은 목록이 존재하는지 | `groupCount`, `itemsPerGroup` | AI 생성 | 목록 요소의 정의에 부합 |
| `form-label` | 구역 내 모든 폼 컨트롤에 레이블이 연결되었는지 | 없음 | AI 생성 | 접근성 필수 요건 |
| `layout-result` | N개 형제 말단 요소의 렌더 측정값이 기대 배치와 일치하는지 | `columns`, `rows` | AI 생성 | 측정 가능한 객관적 기준 |
| `heading-hierarchy` | 지정된 두 요소의 제목 레벨 상하 관계 | — | **보류** | 아래 참조 |

**대상 지정 방식 — 구조 패턴**

판정은 **구역 범위 내의 구조 패턴**으로 수행하며, 특정 요소를 지목하지 않습니다.

`target` 필드는 구조 트리의 역할명(예: "제품 타일")이며 학습자 코드에 존재하지 않는 문자열입니다. 태그와 클래스 이름이 자유 등급이므로 셀렉터로 삼을 수 없고, 문자열을 해석해 대상을 추정하는 것은 F-02-12의 원칙에 반합니다.

**따라서 `target`은 판정에 사용하지 않으며 표시 문구용으로만 유지합니다.** `desc`와 동일한 위치입니다.

AI가 기계 판독 가능한 식별자(노드 경로 등)를 생성하는 방안은 채택하지 않았습니다. 학습자 DOM이 AI의 구조 트리와 같은 형태일 이유가 없으므로 경로가 일치하지 않습니다.

**`heading-hierarchy` 보류**

이 유형은 8.3 검증에서 AI가 `heading-order`에 잘못 담은 조건을 정식화한 것으로, 설계상 필요에서 도출된 것이 아닙니다.

구조 패턴으로 정의하려면 두 대상을 특정해야 하므로 다른 유형과 성격이 다릅니다. 한편 구역 제목과 항목 제목의 관계는 `heading-order`가 상당 부분 포착합니다(구역 제목이 `h2`인데 항목 제목이 `h4`이면 건너뜀으로 검출).

**6개 유형으로 검증을 수행한 뒤 실제 필요성을 판단합니다.** 현 단계에서는 화이트리스트에서 제외합니다.

**생성 주체 구분:** `heading-order`와 `heading-single`은 파라미터가 없고 검사 내용이 고정되어 AI가 생성할 필요가 없습니다. 판정 엔진이 결합 문서에 대해 항상 검사하며 `rubric`에 포함되지 않습니다. 상세는 6.5를 참조하십시오.

**유형 추가 시 주의:** 본 표가 화이트리스트의 유일한 출처입니다. 유형을 추가하거나 변경할 때 다른 절의 목록을 함께 수정할 필요가 없어야 하며, 만약 그런 상황이 발생하면 중복이 생긴 것이므로 제거해야 합니다.

**문서 경계를 넘는 단일 출처**

이 규칙은 PRD 내부뿐 아니라 **AI 프롬프트를 포함한 모든 산출물에 적용됩니다.** 프롬프트에 목록을 하드코딩하지 않고 생성 시점에 본 표를 주입합니다.

과거 `heading-hierarchy`를 추가했을 때 프롬프트의 사본이 갱신되지 않아 즉시 불일치가 발생한 사례가 있습니다. 사본이 존재하는 한 같은 사고가 반복됩니다.

**구현 요건 — 단일 상수에서 파생**

본 문서는 마크다운이므로 코드가 직접 읽을 수 없습니다. 실제 주입 문자열은 코드 내 상수가 됩니다. 이때 **주입 텍스트와 스키마 검증용 열거형을 별도로 정의하면 중복이 문서에서 코드로 자리만 옮긴 것이 됩니다.**

두 산출물은 하나의 상수에서 파생되어야 합니다.

```
조건 유형 상수 (단일 정의)
├─ 프롬프트 주입 텍스트 생성
└─ 스키마 검증 열거형 생성
```

이렇게 하면 "프롬프트가 제시한 유형"과 "검증이 통과시키는 유형"이 구조적으로 어긋날 수 없으며, 일치 여부를 사람이 확인할 필요가 없습니다. 본 표는 그 상수가 구현해야 할 명세로 남습니다.

**파라미터 검증**

각 유형이 요구하는 파라미터가 누락되거나 형식이 맞지 않으면 해당 조건을 거부합니다. 예를 들어 `layout-result`에 기대 배치 값이 없으면 판정이 불가능하므로 유입시키지 않습니다.

**거부 시 처리**

- 조건을 폐기하고 로그를 남깁니다
- 필수 조건이 하나도 남지 않은 구역은 재생성을 요청합니다
- 거부 빈도는 프롬프트 품질 측정에 활용합니다

**`desc` 분리가 덮지 못하는 범위**

판정 로직 고정은 **검사 방식**을 AI 출력에서 분리한 것이며, 다음 두 경로는 여전히 AI 출력에 의존합니다.

| 경로 | 내용 | 대응 |
|---|---|---|
| 학습자에게 보이는 문구 | `desc`가 실제 판정과 어긋나면 학습자는 무엇을 고쳐야 할지 알 수 없음 | 실패 문구를 `type`별 고정 템플릿 + 파라미터로 생성 (F-07-07) |
| 기대값 | `layout-result`의 기대 배치, `list-grouping`의 반복 개수 등은 AI가 생성하고 코드가 신뢰함 | 8.2 검증으로 포착 |

**기대값 오류의 성격:** AI가 3열 2행을 2열 3행으로 잘못 읽으면, 고정 코드는 그 잘못된 기대값을 충실히 판정합니다. 검사 로직이 정확해도 결과는 틀립니다. 이 경로는 판정 계층에서 차단할 수 없으며 8.2 검증에서 포착해야 합니다.

**다중 해석 허용 — 격자 구조 대응**

8.3 재현성 검증에서 동일 시안을 3회 분석한 결과, 2차원 격자 구조에 대해 서로 다른 해석이 나왔습니다.

| 해석 | `list-grouping` 반복 수 | 구조 |
|---|---|---|
| A | 6 | 타일 6개의 평면 나열 |
| B | 3 | 행 3개, 각 행에 타일 2개 |

**두 해석 모두 타당하며, 시안 이미지에는 어느 쪽인지 판별할 정보가 없습니다.** 프롬프트를 개선해도 해소되지 않습니다. 사람이 보아도 갈리는 판단이기 때문입니다.

문제는 어느 해석이 저장되었는지에 따라 **동일한 코드가 정반대로 판정된다**는 점입니다.

| 학습자 코드 | 해석 A 기준 | 해석 B 기준 |
|---|---|---|
| 타일 6개를 하나의 목록에 나열 | 통과 | 실패 |
| 행 단위로 묶고 각 행에 타일 배치 | 실패 | 통과 |

**대응: 파라미터를 단일값이 아닌 허용 집합으로 정의합니다.**

둘 다 올바른 구현이라면 둘 다 통과시켜야 합니다. 하나를 선택하는 것은 4.6.1의 기본 원칙(오탐 방지)에 반합니다.

```json
{
  "type": "list-grouping",
  "target": "제품 타일",
  "accept": [
    { "groupCount": 1, "itemsPerGroup": 6 },
    { "groupCount": 3, "itemsPerGroup": 2 }
  ]
}
```

```json
{
  "type": "layout-result",
  "target": "제품 타일",
  "accept": [
    { "columns": 2, "rows": 3 }
  ]
}
```

`layout-result`의 `accept`는 항상 1개입니다. 말단 요소의 기하 정보로만 기술합니다.

**판정 규칙:** `accept` 배열 중 **하나라도** 만족하면 통과입니다.

**적용 대상은 `list-grouping` 뿐입니다**

| type | `accept` 다중 항목 | 사유 |
|---|---|---|
| `list-grouping` | **허용** | 렌더 결과가 같아도 DOM 그룹 단위가 실제로 다르며, 시안으로 판별 불가 |
| `layout-result` | **불허 (항상 1개)** | 아래 참조 |
| 그 외 5개 유형 | 불허 | 파라미터가 없거나 대상 식별만 필요 |

**`layout-result`에 다중 해석을 두지 않는 이유**

중첩 배치와 평면 배치는 렌더된 말단 요소의 좌표가 동일합니다. 이는 Flex/Grid 선택과 같은 층위의 구현 차이이며, 4.6.5의 렌더 결과 판정이 이미 흡수하도록 설계되어 있습니다.

8.3 재현성 검증에서 3회차가 `1열 3행 + 행 내부 2열`을 낸 것은 해석이 갈린 것이 아니라 **DOM 중첩 구조를 배치 조건에 기술한 것**이며, 4.6.3의 기존 규칙("배치 조건은 결과로 기술, 구현 방식 금지") 위반입니다. 새로운 기능이 아니라 기존 규칙의 준수로 해결됩니다.

따라서 `layout-result`의 기대값은 **말단 요소의 기하 정보로만 기술합니다.**

| 잘못됨 | 올바름 |
|---|---|
| `1열 3행 + 행 내부 2열` | `{ columns: 2, rows: 3 }` |

`accept`를 열어두면 미탐 표면만 넓어집니다.

**문서 전체 범위 조건의 구역별 모드 적용**

`heading-single`과 `heading-order`는 문서 전체를 대상으로 하는 조건입니다. 구역별 모드에서는 학습자가 한 구역만 작성하므로 적용 방식을 정의해야 합니다.

| 조건 | 범위 | 구역 단독 판정 시 문제 |
|---|---|---|
| `heading-single` | 문서 내 `h1` 1개 | 헤더 외 구역에는 `h1`이 없는 것이 정상인데 오탐 발생 |
| `heading-order` | 제목 레벨 건너뜀 없음 | 앞 구역의 제목 레벨을 모르면 판단 불가 |

**채택: 이전 구역들의 확정 HTML을 이어붙여 문서 전체로 판정합니다.**

판정 시점에 통과 완료된 구역들의 HTML과 현재 작성 중인 구역의 HTML을 순서대로 결합하여 하나의 문서를 구성한 뒤 검사합니다. 첫 구역 작성 시에는 앞선 코드가 없으므로 자연스럽게 해당 구역만 검사 대상이 됩니다.

**결합 범위 (엄격히 한정)**

| 항목 | 결합 여부 |
|---|---|
| HTML | 결합 |
| **CSS** | **결합하지 않음** |
| 적용 조건 | **`heading-single`, `heading-order` 두 유형에만 적용** |
| 그 외 모든 조건 | 현재 구역 문서로 판정 |

**CSS를 결합하지 않는 이유**

구역별로 작성하므로 클래스 이름이 겹치는 것은 자연스러우며, 클래스 네이밍은 자유 등급(4.6.2)이라 판정 대상이 아닙니다. 결합 시 구역 4의 `.card { display: block }`이 구역 2의 동명 요소를 덮어써, 학습자가 잘못한 것이 없는데 판정이 틀어집니다.

결합이 필요한 두 유형은 DOM 구조만 보므로 CSS가 필요하지 않습니다.

**`layout-result`를 결합 문서로 판정하지 않는 이유**

3열 미리보기는 현재 구역만 렌더링합니다. 결합 문서에서 배치를 측정하면 학습자가 화면에서 보는 것과 판정 근거가 달라지며, **실패 원인을 화면에서 확인할 수 없어 학습이 성립하지 않습니다.** F-07-07(실패 문구와 실제 판정의 일치)과 동일한 이유입니다.

`heading-single`과 `heading-order`는 애초에 "문서 전체"가 조건의 근거이므로, 현재 구역 화면에 보이지 않는 것을 근거로 판정해도 학습자가 납득할 수 있는 종류입니다.

**다른 방안을 택하지 않은 이유**

| 방안 | 배제 사유 |
|---|---|
| 두 유형을 통짜 모드 전용으로 한정 | 제목 계층은 시맨틱 훈련의 핵심이므로 구역별 모드에서 제외하면 손실이 큼 |
| 구역 단위로 범위 재해석 (구역 내 최상위 제목 1개) | `heading-single`의 의미가 왜곡됨. 구역마다 `h1`이 하나씩 있어도 된다는 잘못된 학습이 발생 |

**부수 요구사항 — 선행 구역 변경 시 재검증**

완료 구역 재진입(F-08-03)이 허용되므로, 앞 구역의 제목 구조를 변경하면 이후 구역의 판정 결과가 달라질 수 있습니다. 예를 들어 헤더의 `h1`을 `h2`로 바꾸면 이후 구역들이 `heading-single`을 위반하게 됩니다.

**처리: 통과 상태를 유지하고 "재확인 필요" 표시만 남깁니다.**

| 항목 | 처리 |
|---|---|
| 통과 상태 | 유지 |
| 후속 구역 개방 | 유지 (잠그지 않음) |
| 시도 횟수 | 차감하지 않음 |
| 표시 | 해당 구역에 재확인 필요 표시, 원인 구역 안내 |

**통과 취소를 택하지 않은 이유**

실패 원인이 해당 구역이 아니라 다른 구역의 변경입니다. 구역 5를 작성 중인 학습자가 구역 1을 수정했다고 구역 2~4가 잠기면 진행이 통째로 되돌아가며, 실질적으로 "완료 구역을 재진입하지 말라"는 신호가 되어 F-08-03을 무력화합니다.

진행을 막기보다 어디를 손봐야 하는지 알려주는 편이 학습 흐름에 맞습니다.

**`accept` 항목의 제약**

`accept` 항목이 늘어날수록 조건은 약해지므로 무제한 허용하지 않습니다.

- `accept`의 모든 항목은 **동일한 시각적 결과를 낳는 구현**이어야 합니다
- 시각적 결과가 다른 해석을 나열하는 것은 조건 무력화이며 거부 대상입니다

**AI 프롬프트 요구사항:** 2차원 격자 구조에서 `list-grouping`의 그룹 단위가 갈릴 때만 `accept`에 복수 항목을 나열합니다. `layout-result`는 항상 1개입니다.

#### 4.6.5 판정 방식

| 대상 | 방식 |
|---|---|
| 시맨틱 | DOM 구조를 역할 기준으로 정규화한 뒤 조건 충족 검사 |
| 레이아웃 | **렌더링 결과 측정** — `getBoundingClientRect()`, `getComputedStyle()`로 실제 계산된 위치·크기 비교 |

레이아웃을 렌더 결과로 판정하므로 Flex·Grid·float 등 구현 방식의 차이는 자동으로 해소됩니다. 결과가 조건을 만족하면 통과입니다.

**측정 통로 — 확정 (검증 완료)**

`sandbox` 속성의 `allow-same-origin`과 `allow-scripts`는 독립된 플래그입니다. `allow-same-origin` 단독 부여 시 부모 문서에서 `contentDocument` 접근이 가능해지지만, `allow-scripts`가 없으므로 문서 내 어떤 스크립트도 실행되지 않습니다.

따라서 **측정 스크립트를 주입할 필요 없이** 부모가 직접 `getBoundingClientRect()`와 `getComputedStyle()`을 호출합니다. "주입 스크립트만 실행하고 사용자 스크립트는 차단"이라는 쟁점 자체가 발생하지 않습니다.

| 구성 | `contentDocument` | 사용자 스크립트 |
|---|---|---|
| `sandbox=""` | 접근 불가 | 차단 |
| `sandbox="allow-same-origin"` | **접근 가능** | **차단** |
| `sandbox="allow-scripts"` + CSP nonce | 접근 불가 (`postMessage` 필요) | 차단 |

**위험한 것은 `allow-scripts`와 `allow-same-origin`의 동시 부여이며, `allow-same-origin` 단독 부여가 아닙니다.**

**검증된 차단 경로**

- 인라인 `<script>`
- `<img onerror>`
- `javascript:` URL (`click()` 호출까지 확인)
- 중첩 iframe으로 권한 확대 시도 — 샌드박스 플래그는 상속되며 자식이 넓힐 수 없음

CSP `script-src 'none'`을 문서에 함께 주입합니다. 측정값에 영향이 없고, 향후 누군가 `allow-scripts`를 실수로 추가해도 스크립트가 실행되지 않는 이중 차단이 됩니다.

**`allow-scripts` + CSP nonce 방식을 택하지 않은 이유**

동작은 하나 두 가지가 불리합니다. 첫째, 주입 스크립트가 파싱 중 실행되어 레이아웃 확정 전에 측정하는 문제가 있으며(실측 시 `width: 0`), 이를 해결하려면 부모가 측정을 요청하고 회신을 기다리는 왕복 구조가 필요합니다. 둘째, nonce 유출 시 사용자 스크립트에 부착될 여지가 있어 검증 부담이 늘어납니다.

**판정 전용 iframe 분리**

미리보기 iframe과 판정용 iframe을 분리합니다. 격리 수준이 아니라 **측정값의 결정성** 때문입니다.

3열 미리보기는 사용자가 경계선을 드래그해 너비를 변경합니다. 그 상태에서 측정하면 "카드 3개가 가로 한 줄"과 같은 조건이 열 너비에 따라 통과와 실패를 오갑니다. 판정은 결정적이어야 하므로 시안 너비에 맞춘 고정 폭에서 측정해야 합니다.

| iframe | sandbox | 용도 |
|---|---|---|
| 미리보기 (3열, 가시) | `""` | 학습자가 보는 화면. 격리 최대 |
| 판정용 (숨김, 고정 폭) | `allow-same-origin` + CSP | 확인 버튼 클릭 시에만 생성, 측정 후 파기 |

완화된 오리진을 갖는 문서의 수명이 판정 순간으로 제한되며, 1단계 구현의 미리보기는 변경하지 않습니다.

#### 4.6.6 회색지대 처리

`<ul><li>` 대 `<div><article>` 처럼 양쪽 모두 타당한 경우는 **필수에서 제외하고 권장으로 배치**합니다. 통과시키되 대안을 안내하는 방식이 학습 도구로서 더 적절합니다.

#### 4.6.7 이미지가 뜨지 않는 상태에서의 배치 측정

판정용 문서와 미리보기는 모두 격리된 문서라 학습자가 쓴 이미지 경로가 실제 파일을 가리키지 않습니다. 따라서 **배치는 항상 이미지가 깨진 상태에서 측정됩니다.**

두 프레임의 동작이 다릅니다.

| | 판정용 `allow-same-origin` | 미리보기 `sandbox=""` |
|---|---|---|
| 절대 경로 `/x.jpg` | 앱 오리진 기준으로 해석됨. 파일이 있으면 로드 | **요청 자체가 나가지 않음** |
| 전체 URL | 해석됨 | **요청 자체가 나가지 않음** |
| `data:` URL | 로드됨 | 로드됨 |

미리보기가 이미지를 전혀 부르지 않는 것은 base URL이 없어서가 아니라 **불투명 오리진** 때문입니다. `<base>`를 넣어도 달라지지 않으므로, 이 문제를 이유로 iframe에 무언가를 주입할 근거는 없습니다.

**측정 결과 — 11개 경우 중 1개만 오탐**

`layout-result`(3열 1행)를 실제 판정 경로로 쟀습니다. flex·inline-block·폭 %·폭 auto를 바꿔가며 재도 배치 판정은 유지됩니다. 이미지가 깨져도 감싸는 요소나 대체 텍스트 상자가 자리를 지키기 때문입니다.

**세 조건이 동시에 성립할 때만 실패합니다.**

1. 이미지가 감싸는 요소 없이 반복 항목 그 자체이고
2. CSS로 크기를 지정하지 않았으며
3. `alt=""`이다

이때만 이미지가 `0×0`이 되어 묶을 박스가 사라집니다. 셋 중 하나만 어긋나도 통과합니다. 대체 텍스트가 있으면 깨진 이미지가 상자(약 62×20)를 만들고, 감싸는 요소가 있으면 그쪽이 폭을 정합니다.

**받아들이는 이유.** 조건 ③은 의미 있는 이미지를 장식으로 표시한 것이므로 학습자 쪽 오류가 선행합니다. 그 오류는 `image-alt`가 잡지 않기로 한 것이고(1.4 비목표), 이를 잡으려면 `target`을 판정에 끌어들여야 합니다. 판정 로직에서 `0×0` 요소를 특별 취급하면 진짜로 배치가 무너진 경우까지 놓쳐 미탐이 늘어납니다.

**대신 모범 예시가 이미지 크기를 항상 지정하도록** 3단계 프롬프트에 명시했습니다(조건 ②를 깨뜨립니다). 실무에서도 이미지 자리를 미리 잡는 것이 권장 관행이므로 학습 내용과 어긋나지 않습니다.

**F-07-07 상세 — 실패 문구 생성**

판정은 `type`별 고정 코드가 수행하므로(4.6.4), 학습자에게 표시할 실패 문구도 동일한 출처에서 생성해야 합니다. AI가 작성한 `desc`를 그대로 표시하면 실제 판정 내용과 어긋날 수 있습니다.

**어긋난 경우의 문제**

`heading-order`로 판정되어 `h1` → `h3` 건너뜀이 걸렸는데, 화면에 "제품명이 구역 제목보다 하위 계층일 것"이라고 표시되면 학습자는 무엇을 고쳐야 할지 알 수 없습니다. 판정이 정확해도 학습이 성립하지 않습니다.

| 요소 | 역할 |
|---|---|
| 고정 템플릿 + 파라미터 | 실패 문구의 주 출처 |
| `desc` | 조건 목록 표시 등 보조 용도 |
| `hints` | 회차별 힌트. 판정 결과와 별개 |

**엔진 상시 조건의 힌트**

`heading-single`과 `heading-order`는 `rubric`에 포함되지 않으므로(F-08-09) `hints` 필드가 존재하지 않습니다. 이 두 유형의 회차별 힌트는 **실패 문구 템플릿과 함께 코드에 고정 정의**합니다.

두 유형은 파라미터가 없고 검사 내용이 고정되어 있어 힌트도 고정할 수 있습니다. 엔진이 검사하는 조건은 엔진이 설명한다는 점에서 F-02-12와 방향이 같으며, AI 생성보다 문구가 일관됩니다.

| 회차 | `heading-single` 예 |
|---|---|
| 1 | 문서 전체의 제목 구조를 확인해보세요. |
| 2 | 페이지에서 가장 상위 제목이 몇 개인지 세어보세요. |
| 3 | 최상위 제목은 문서에 하나만 두어야 합니다. |

**F-07-05 / F-07-06 상세 — 코드 복사 정책**

| 대상 | 복사 기능 | 사유 |
|---|---|---|
| 모범 예시 코드 | 제공하지 않음 | 복사·붙여넣기로 통과하는 경로를 기본 동선에서 제거. 예시를 보며 직접 작성하는 것이 학습 과정 |
| 사용자 작성 코드 | 제공 가능 | 본인 결과물의 외부 활용을 제한할 이유 없음 |

브라우저 기본 텍스트 선택으로 복사하는 것은 차단하지 않습니다. 본 정책은 기술적 차단이 아니라 **기본 동선 설계**에 관한 것입니다.

앱 크롬은 다크입니다. 색은 모두 CSS 변수로 정의합니다.

**미리보기와 시안은 밝은 채로 둡니다.** 이 제약은 여전히 유효합니다.

- 미리보기 iframe 내부에 어떤 스타일도 주입하지 않습니다. 리셋 CSS, 다크 배경, `color-scheme` 모두 금지입니다. 학습자는 브라우저 기본 스타일 위에 자기 CSS만 얹힌 상태를 관찰해야 하며, 이는 4.5의 전제입니다
- 판정용 iframe도 같습니다. 스타일이 들어가면 측정값이 달라져 8.2의 결과가 무효가 됩니다

당초 이 제약 때문에 다크 모드를 비목표로 두었습니다. **제약을 없애는 대신 디자인으로 흡수합니다** — 미리보기와 시안 열을 어두운 프레임으로 감싸 흰 배경이 창 안의 페이지로 읽히게 합니다. 실제 브라우저도 흰 페이지를 띄우므로 자연스럽고, 두 열이 같은 프레임을 쓰면 "양쪽은 참조 대상, 가운데는 작업 영역"이라는 구분이 생깁니다.

스크롤바와 네이티브 컨트롤을 위해 앱 문서에 `color-scheme: dark`를 두되, iframe 요소에는 부모 측에서 `color-scheme: light`를 명시합니다. iframe 내부에 주입하는 것이 아니라 브라우저가 그 프레임을 다루는 방식을 지정하는 것이며, 위 제약을 지키는 방향입니다.

**대비는 계산으로 확인합니다.** 이 도구가 접근성을 가르치므로 스스로 지키지 않으면 앞뒤가 맞지 않습니다. 본문·보조 텍스트와 에디터 토큰 모두 WCAG AA(4.5:1)를 넘겨야 하며, 에디터 토큰은 에디터 배경뿐 아니라 **활성 줄과 선택 영역 배경 위에서도** 기준을 넘겨야 합니다. 실제로 이 조건이 선택 영역 색을 파랑에서 중성 회색으로 바꾸게 했습니다.

구역 편집 화면의 오버레이는 크롬이 아니라 **시안 이미지 위에 얹힙니다.** 시안은 대개 밝으므로 비선택 구역은 검정 계열로 덮습니다. 크롬 색 토큰을 쓰면 다크 테마에서 밝은 워시가 되어 밝은 시안 위에서 사라집니다.

## 6. 데이터 구조

4.6.4의 판정 설계와 F-08-05의 결합 판정에 맞춘 구조입니다.

**본 장이 데이터 형태의 단일 출처입니다.** AI 프롬프트의 출력 예시는 본 장을 따릅니다. 필드가 변경되면 본 장을 먼저 수정하고 프롬프트를 뒤따라 갱신합니다. 서로를 버전 번호로 참조하지 않습니다(4.6.4의 단일 출처 규칙과 동일한 취지).

### 6.1 소스 (콘텐츠 루트)

```json
{
  "id": "src-001",
  "title": "쇼핑몰 메인",
  "createdAt": "2026-08-31T10:00:00Z",
  "source": {
    "type": "image",
    "file": "design.png",
    "width": 1440,
    "height": 8200
  },
  "settings": {
    "mode": "sectioned",
    "maxAttempts": 3
  },
  "mainTitleSectionId": "sec-02",
  "reference": {
    "colors": { "주요": "#000000", "배경": "#ffffff" },
    "spacing": "구역 간 여백은 대략 80px"
  },
  "sections": [ ],
  "progress": { }
}
```

| 필드 | 비고 |
|---|---|
| `stage` | 등록 절차의 진행 단계. 아래 참조 |
| `mainTitleSectionId` | 최상위 제목이 위치한 구역. 문서 전체 범위 조건의 검사 시작 지점 (F-08-10). 1단계 분석이 생성하며 `sections`에 존재하는 id여야 함 |
| `reference` | 학습자에게 보조 정보로 표시. 판정에 사용하지 않음 (1.4 비목표) |

**`stage`** — 분석이 두 시점으로 나뉘므로(3장) 그 사이 상태를 구분할 값이 필요합니다.

| 값 | 의미 |
|---|---|
| `structure-pending` | 등록만 된 상태. 구조 분석 전이거나 실패 |
| `sections-pending` | 구조 분석 완료. 구역 확정 대기 |
| `ready` | 조건·예시까지 생성됨. 학습 가능 |

`mainTitleSectionId`가 `null`이거나 존재하지 않는 구역을 가리키면 스키마 검증에서 거부하고 재생성을 요청합니다. **`role` 문자열을 해석해 추정하지 않습니다**(F-02-12의 문자열 미의존 원칙과 동일).

### 6.2 구역

```json
{
  "id": "sec-03",
  "name": "제품 타일",
  "order": 3,
  "bounds": { "topRatio": 0.21, "heightRatio": 0.18 },
  "sameStructureAs": null,
  "structure": { },
  "rubric": [ ],
  "example": { "html": "", "css": "" }
}
```

| 필드 | 비고 |
|---|---|
| `bounds` | **비율로 저장합니다.** 업로드 이미지의 크기가 제각각이므로 픽셀값은 사용할 수 없습니다 |
| `sameStructureAs` | 동일 구조 반복 구역 표시 (F-02-09) |
| `structure` | 1단계 분석의 의미 구조 트리. 격자는 평면으로 저장 |
| `example` | 3단계에서 생성된 모범 예시. 시도 소진 시 공개 (F-07-02) |

### 6.3 판정 조건

AI 분석 2단계의 출력 형식이며, 본 절이 출처입니다.

```json
{
  "id": "r1",
  "level": "required",
  "type": "list-grouping",
  "target": "제품 타일",
  "accept": [
    { "groupCount": 1, "itemsPerGroup": 6 },
    { "groupCount": 3, "itemsPerGroup": 2 }
  ],
  "desc": "반복되는 제품 타일 6개를 목록으로 묶을 것",
  "hints": {
    "1": "제품 영역의 구조를 다시 확인해보세요.",
    "2": "타일이 같은 구조로 반복되고 있습니다.",
    "3": "반복되는 항목은 목록 요소로 묶습니다."
  }
}
```

| 필드 | 규칙 |
|---|---|
| `type` | 4.6.4의 열거형. 스키마 검증 대상 |
| `target` | **표시용. 판정에 관여하지 않음** (4.6.4). 구조 트리의 역할명 |
| `accept` | 파라미터 배열. 하나라도 만족하면 통과. `layout-result`는 항상 1개 (F-02-14) |
| `desc` | **표시용. 판정에 관여하지 않음** (4.6.4) |
| `hints` | **조건마다 1세트.** 회차별 수위 3단계 (F-07-01) |

**`hints`가 조건 단위인 이유:** 구역당 하나면 어떤 조건이 실패했는지에 따라 힌트를 선택할 수 없습니다.

**`desc`가 판정에 관여하지 않으므로**, 학습자에게 표시할 실패 문구는 `type`별 고정 템플릿과 `accept` 파라미터로 생성합니다(F-07-07).

`level`이 `recommended`인 항목은 `type`이 `semantic-suggestion`이며 `accept`와 `hints`를 갖지 않습니다.

### 6.4 진행 상태

**구역별 코드를 개별 보관합니다.** F-08-05의 결합 판정과 F-08-03의 완료 구역 재진입이 모두 이 구조를 전제합니다.

```json
{
  "currentSection": "sec-03",
  "sections": {
    "sec-01": {
      "status": "passed",
      "attemptsUsed": 1,
      "code": { "html": "<header>...</header>", "css": "header { ... }" },
      "needsRecheck": false,
      "recheckCause": null
    },
    "sec-02": {
      "status": "passed",
      "attemptsUsed": 2,
      "code": { "html": "...", "css": "..." },
      "needsRecheck": true,
      "recheckCause": "sec-01"
    },
    "sec-03": {
      "status": "in_progress",
      "attemptsUsed": 0,
      "code": { "html": "", "css": "" },
      "needsRecheck": false,
      "recheckCause": null
    }
  }
}
```

| 필드 | 값 |
|---|---|
| `status` | `locked` / `in_progress` / `passed` / `revealed` |
| `attemptsUsed` | 소진 시 `example` 공개 |
| `code` | 구역별 작성 코드. 자동 저장 (F-04-10) |
| `needsRecheck` | 선행 구역 변경으로 재검증 필요 (F-08-06) |
| `recheckCause` | 원인 구역 id. 학습자에게 안내 |

`status`가 `revealed`는 시도를 소진해 모범 예시가 공개된 상태입니다. 통과와 구분해 기록합니다.

**`needsRecheck`가 `true`여도 `status`는 `passed`를 유지하며 후속 구역을 잠그지 않습니다**(F-08-06). 실패 원인이 해당 구역이 아니기 때문입니다.

### 6.5 결합 판정 입력

`heading-single`과 `heading-order` 판정 시에만 구성합니다(F-08-05).

```
결합 대상 = 아래 구역들을 order 순으로 정렬해 이어붙인 HTML

  status = passed    → 해당 구역의 code.html
  status = revealed  → 해당 구역의 example.html   ← 학습자 코드가 아님
  현재 구역          → 작성 중인 code.html
```

**현재 구역은 자기 `order` 자리에 들어갑니다.** 맨 뒤에 붙이지 않습니다.

F-08-03으로 완료 구역에 재진입하면 현재 구역이 마지막이 아닙니다. 구역 2로 돌아간 경우 `[1, 3, 4, 5] + [2]` 순서로 결합하면 `heading-order`가 문서 순서대로 제목 레벨을 검사하므로 정상 코드가 건너뜀으로 잡힙니다.

**현재 구역보다 뒤에 있는 통과 구역도 포함합니다.** 구역 4에 `h1`이 있는데 구역 2를 다시 작성 중이라면, 구역 4를 제외할 경우 구역 2가 `h1`을 가져야 통과하게 되어 잘못된 학습을 유도합니다.

**`revealed` 구역은 `example.html`을 사용합니다**

`revealed`는 시도를 소진해 예시가 공개된 상태이며, **정의상 판정을 통과하지 못한 구역입니다.** 학습자 코드를 결합하면 그 구역의 위반이 이후 모든 구역으로 전파됩니다.

예를 들어 구역 1에서 `h1`을 둘 작성한 채 소진하면, 이후 모든 구역의 결합 문서에 `h1`이 둘 이상 포함되어 **구역 2를 어떻게 작성해도 `heading-single`을 통과할 수 없습니다.** 학습자는 자기 코드에 문제가 없는데 계속 실패하며, 힌트는 현재 구역 조건만 다루므로 원인을 알 수 없습니다.

예시가 이미 공개된 구역이므로 학습자도 해당 코드를 확인한 상태이며, 문서가 항상 올바른 기준선에서 이어집니다.

**요구사항:** 판정 근거에 학습자가 작성하지 않은 코드가 포함되므로, 해당 구역이 예시 코드로 대체되었음을 화면에 명시합니다(F-08-08).

**두 유형은 rubric에 포함되지 않습니다**

`heading-single`과 `heading-order`는 **AI가 생성하지 않으며 특정 구역의 `rubric`에 배치되지도 않습니다.** 판정 엔진이 매 판정마다 결합 문서 전체에 대해 항상 검사합니다.

**AI 배치에 맡길 수 없는 이유 — 데드락**

두 유형을 AI가 구역별 `rubric`에 배치하면 다음이 발생합니다. 시안의 최상위 제목이 구역 2에 있는데 `heading-single`이 구역 1에 배치된 경우입니다.

1. 구역 1 판정 시점의 결합 문서는 구역 1뿐입니다 (구역 2 이후는 `locked`)
2. 헤더에 `h1`이 없는 것은 정상이므로 실패
3. F-08-02에 따라 구역 2는 잠겨 있어 `h1`을 작성할 곳이 없음
4. 통과하려면 시안과 어긋나는 마크업을 작성해야 함

**결합 판정을 도입해도 첫 구역에서는 결합할 선행 구역이 없으므로 이 오탐이 그대로 남습니다.**

**적용 시작 구역**

1단계 분석이 반환한 `mainTitleSectionId` 구역부터 두 유형을 검사합니다. 이전 구역에서는 건너뜁니다.

**전용 필드를 두는 이유:** 구조 트리의 `role`은 자유 서술 문자열이며, 절대 규칙상 태그명(`h1` 등)을 쓰지 않으므로 제목 레벨을 표현할 수단이 없습니다. 엔진이 문자열을 추측해 시작 구역을 정하면 F-02-12(문자열 미의존)와 어긋납니다.

| 구역 | 최상위 제목 위치가 구역 2일 때 |
|---|---|
| 구역 1 | 검사하지 않음 |
| 구역 2 이후 | 결합 문서 전체에 대해 검사 |

**역방향 위반도 함께 처리됩니다**

F-08-06은 "선행 구역 변경 → 후속 구역 재검증"만 다루나, `h1` 중복은 반대 방향입니다. 구역 4에서 `h1`을 추가하면 이미 통과한 구역 2가 위반 상태가 됩니다.

매 판정마다 결합 문서 전체를 검사하므로 이 방향도 자연히 포착됩니다. 별도 규칙이 필요하지 않습니다.

| 항목 | 처리 |
|---|---|
| HTML | 결합 |
| **CSS** | **결합하지 않음** (F-08-07) |
| 적용 조건 | `heading-single`, `heading-order` 두 유형만 |
| 그 외 조건 | 현재 구역 문서로 판정 |

### 6.6 통짜 모드

`settings.mode`가 `whole`인 경우 `sections`는 항목 하나만 가지며, 그 구역이 시안 전체를 범위로 합니다. 결합 판정(6.5)은 불필요하며 조건 판정이 모두 단일 문서에서 수행됩니다.

**구역 수 상한 — 5개**

구조 분석이 나눈 구역이 5개를 넘으면 통짜로 진행하지 않고 구역별 모드로 전환하며, 사용자에게 이유를 알립니다. 모드는 등록 시점에 고르지만 구역 수는 분석이 끝나야 알 수 있으므로 **검사 시점은 구조 분석 직후**입니다.

*근거 — 11구역 시안을 통짜로 끝까지 돌린 결과*

| | 구역별 | 통짜 |
|---|---|---|
| 필수 조건 | 30개를 11번에 분산 (구역당 0~5개) | 16개를 한 번에 |
| 총 시도 | 33회 (구역당 3회) | 3회 |
| 실패 시 피드백 | 최대 5건 | 16건 동시 (1,248자) |
| 모범 예시 | 최대 2,343자 | 16,937자 한 덩어리 |
| 조건 생성 | 요청당 55초 | 205초 |

기능은 모두 정상 동작했습니다. 성립하지 않는 것은 학습 흐름입니다.

1. **시도 3회를 조건 16개가 공유합니다.** 하나라도 틀리면 실패이므로 사실상 세 번 안에 전부 맞혀야 합니다.
2. **힌트 단계 설계가 무력화됩니다.** `hintTier`(4.7)는 시도 횟수로 올라가는데, 모든 조건이 같은 카운터를 공유하므로 이미 이해한 조건의 힌트까지 함께 구체화됩니다. 수위를 3단계로 나눈 의도가 작동하지 않습니다.
3. **피드백 16건을 동시에 받습니다.** 어디부터 손대야 할지 학습자가 정할 수 없습니다.
4. **부분 성취가 남지 않습니다.** 통과한 구역이 쌓이지 않는 all-or-nothing입니다.
5. **조건은 성겨지는데 난이도는 오릅니다.** 같은 시안에서 30개가 16개로 줄었습니다. 학습 밀도와 난이도가 동시에 나빠집니다.

*상한을 5로 정한 이유*

조건 생성이 구역당 약 19초이므로 5구역이면 약 95초입니다(4구역 실측 97초). 함수 실행 시간 한도 180초 안에 여유 있게 들어옵니다. 학습 부담도 감당할 수준입니다 — 4구역 시안의 통짜는 조건 8개, 예시 4,013자였습니다.

*모드를 폐기하지 않는 이유*

문서 전체를 하나로 설계하는 연습은 구역별 모드로는 기를 수 없습니다. 문제는 모드가 아니라 규모이므로 규모만 제한합니다.

**초과 시 진행을 허용하지 않는 이유**

경고 후 진행을 허용하면 조건 생성이 배포 환경에서 확실히 타임아웃되므로, 로컬에서는 되는데 배포에서만 실패하는 상태가 됩니다. 동작하지 않는 선택지를 남겨 두지 않습니다.

### 6.7 저장 위치

7.3의 저장 항목 표를 참조하십시오. 1단계는 IndexedDB, 이후 Supabase 전환 시 스키마를 그대로 옮길 수 있도록 설계합니다.

F-04-07(이름 제안 토글)이 자동완성을 항목별로 분리 제어할 것을 요구합니다. CodeMirror 6는 `autocompletion()` 확장에 완성 소스를 개별 지정하는 구조이므로 다음 분리가 가능합니다.

| 기능 | 출처 | 제어 |
|---|---|---|
| 태그 이름 제안 | `autocompletion()` | 토글 대상 |

**HTML 속성 제안 포함 사유**

`class`, `alt`, `aria-label` 등 속성 이름 역시 학습자가 직접 떠올려야 할 대상이며, 특히 접근성 속성을 자동 제시하는 것은 시맨틱 훈련을 저해합니다. 태그 제안과 동일하게 토글 대상에 포함합니다.

Monaco Editor는 IDE 지향으로 번들 크기가 크고 완성 항목 분리가 상대적으로 복잡합니다.

### 8.2 판정 정확도 — 검증 완료

**오탐과 미탐을 모두 측정해야 합니다.** 오탐만 측정하는 설계로는 F-05-04에서 발견된 유형(모든 측정값이 0이 되어 무조건 통과)을 잡아낼 수 없습니다.

| 측정 대상 | 방법 | 실패의 성격 |
|---|---|---|
| 오탐률 | 동일 시안에 대해 서로 다른 방식으로 작성한 복수의 정답 코드를 통과시킴 | 학습자가 항의하므로 발견됨 |
| 미탐률 | 조건을 의도적으로 위반한 코드가 실제로 걸리는지 확인 | **조용히 통과하므로 발견되지 않음** |

미탐은 학습자가 잘못된 코드를 정답으로 인식하게 만들므로, 학습 도구에서는 오탐보다 위험합니다.

**검증용 정답 코드는 반드시 시안만 보고 작성합니다**

조건 목록을 참고해 코드를 작성하면 AI가 생성한 기대값에 맞춰 쓰게 되어, 기대값 자체가 틀린 경우(3열 2행을 2열 3행으로 잘못 읽는 등)를 포착할 수 없습니다. 검증이 스스로를 검증하는 구조가 됩니다.

**기대값 오류는 판정 계층에서 차단할 수 없으며(4.6.4), 본 검증이 유일한 포착 경로입니다.**

**미탐 검증 항목 예시**

- 카드를 세로로 쌓아놓고 가로 배치 조건을 통과하는지
- 반복 항목을 목록으로 묶지 않고 `list-grouping` 조건을 통과하는지
- `alt` 없는 이미지가 `image-alt` 조건을 통과하는지
- 제목 계층을 건너뛰고 `heading-order` 조건을 통과하는지
- `accept` 항목이 과도하게 넓어 위반 코드가 통과하는지

**측정 결과**

손으로 작성한 조건과 AI가 생성한 조건 양쪽으로 측정했습니다. 정답 코드는 시안만 보고 먼저 작성해 커밋한 뒤 조건을 만들었습니다.

| 조건 출처 | 오탐 | 미탐 | 비고 |
|---|---|---|---|
| 손으로 작성 | 0/5 | 0/9 | 판정 로직 자체의 동작 확인 |
| AI 생성 (3회 분석) | 0/12 | 1/24 | `layout-result` 대상 단위 지정 전 |
| AI 생성 (3회 분석) | **0/12** | **0/24** | 대상 단위 지정 후 |

정답 코드 4벌은 Flexbox·Grid·inline-block, 평면 나열과 행 중첩, 시맨틱 강·약을 섞어 작성했습니다. 3단계가 만든 모범 예시 3벌도 자기 회차의 조건을 모두 통과했으며, 조건을 보고 만들어진 코드이므로 오탐 집계와 구분했습니다.

유일했던 미탐은 조건이 틀려서가 아니라 **대상 단위가 회차마다 갈려서** 발생했습니다. 상세는 8.3을 참조하십시오.

**한계**

측정에 쓴 시안은 더미 한 장입니다. 표본이 작고, 조건과 정답 코드를 같은 사람이 작성했으며, 폼이 없어 `form-label`은 별도 최소 픽스처로만 확인했습니다. 실제 시안에서의 재측정이 필요합니다.

측정에 쓴 조건 3회분은 픽스처로 고정해 두었습니다. 판정 로직을 고칠 때마다 조건이 달라지면 수치 변화의 원인을 분리할 수 없기 때문입니다.

### 8.3 조건 생성 품질 — 검증 완료

**8.1 검증 결과, 본 도구의 주된 위험은 AI가 구조를 읽지 못하는 것이 아니라 판단이 갈리는 사항을 필수 조건으로 잡는 것으로 확인되었습니다.**

Apple 페이지의 2열 3행 타일 영역은 "그리드 하나"와 "2열 행 3개의 수직 배열" 양쪽으로 해석 가능하며, 마크업이 전혀 달라집니다. 이런 사항이 필수 조건이 되면 오탐이 확정적으로 발생합니다.

**대응:** 4.6.3의 화이트리스트 정책을 도입하고, 4.6.4의 목록·스키마 검증·판정 로직 고정으로 이를 강제합니다.

**1차 검증 결과 (Apple 제품 타일 구역, 프롬프트 v1)**

| 확인 항목 | 결과 |
|---|---|
| 필수 조건이 화이트리스트 내에 있는가 | 통과 |
| `layout-result`에 CSS 속성명이 없는가 | 통과 — "가로 2개씩 3행으로 놓일 것" |
| 그리드/플렉스 판단이 필수로 올라왔는가 | 발생하지 않음 |
| 링크/버튼 판단이 권장에 머물렀는가 | 통과 |
| `article`/`div` 판단이 권장에 머물렀는가 | 통과 |

**발견된 문제 — 유형 오용**

`type`은 유효하나 `desc`가 해당 유형의 정의와 다른 조건을 기술하는 사례가 확인되었습니다.

```json
{ "type": "heading-order", "desc": "제품명이 구역 제목보다 하위 계층일 것" }
```

`heading-order`는 계층 건너뜀을 검사하는 유형이나, 위 조건은 상하 관계라는 별개의 검사입니다. **스키마 검증은 `type` 값만 보므로 이를 통과합니다.**

**대응 완료**

- 판정 로직을 `type`별 고정 코드로 정의하고 `desc`는 판정에 관여하지 않도록 함 (4.6.4)
- 조건 자체는 타당하므로 `heading-hierarchy`를 화이트리스트에 정식 추가 (7개 유형)

**잔여 항목 검증 결과**

| 항목 | 결과 |
|---|---|
| 화이트리스트 이탈 | 3회 분석 모두 이탈 없음 |
| 동일 시안 3회 분석 재현성 | 대상 단위 지정 후 `(type, 파라미터)` 집합 일치 |
| 3단계 예시가 2단계 조건을 만족하는지 | 3/3 통과 |

**재현성 — `layout-result`의 대상 단위**

지정 전에는 3회 중 1회가 머리말을 "로고와 메뉴 두 덩이가 가로"로, 나머지는 "메뉴 항목 4개가 가로"로 읽었습니다. **둘 다 시안에서 참입니다.** 기대값 오독이 아니라 어느 단위를 볼지가 정해지지 않은 문제였습니다.

그 차이는 오탐이 아니라 **미탐으로 나타났습니다.** 정답 코드는 두 조건 모두 만족하지만, 메뉴를 세로로 쌓은 위반 코드가 상위 덩어리 기준에서는 통과했습니다. 로고와 메뉴 블록은 여전히 가로였기 때문입니다.

반복 항목이 있으면 그 항목을 대상으로 삼도록 지시를 좁게 추가해 해소했습니다. 상세는 `docs/analysis-prompt.md`를 참조하십시오.

**재현성 비교 단위: `(type, 파라미터)` 집합**

조건의 개수와 유형만 비교해서는 안 됩니다. 판정 결과를 좌우하는 것은 유형과 파라미터의 조합이기 때문입니다.

| 사례 | 유형 기준 | 실제 |
|---|---|---|
| 3회 모두 `layout-result` 1개, 기대 배치가 "2열 3행 / 2열 3행 / 3열 2행" | 재현 성공 | **실패 — 판정이 뒤집힘** |
| 3회의 `desc` 문구가 모두 다르나 `(type, 파라미터)`는 동일 | 실패 | **성공 — 판정 동일** |

`desc`는 판정에 관여하지 않으므로(4.6.4) 문구 차이는 재현성 실패로 집계하지 않습니다.

**부수 효과 — 기대값 오류 탐지**

3회 분석의 파라미터가 갈리면 최소 2회는 틀린 것이므로, 시안과 대조하기 전에 의심 지점을 좁힐 수 있습니다. 다만 **3회가 일치해도 정확성이 보장되지는 않습니다.** 동일한 방식으로 세 번 오독하는 경우가 가능하므로 8.2 검증은 여전히 필요합니다.

**재현성 검증 결과 (Apple 제품 타일 구역, 3회)**

| 회차 | 조건 구성 |
|---|---|
| 1 | `list-grouping`(반복 6) · `layout-result`(2열 3행) · `image-alt` · `heading-hierarchy` |
| 2 | `list-grouping`(반복 6) · `layout-result`(2열 3행) · `image-alt` |
| 3 | `list-grouping`(그룹 3개, 각 2개) · `layout-result`(1열 3행 + 행 내부 2열) · `image-alt` |

**판정: 재현성 실패.** 두 종류의 불일치가 확인되었습니다.

| 불일치 | 내용 | 영향 |
|---|---|---|
| 조건 개수 | `heading-hierarchy`가 1회차에만 생성됨 | 통과 기준이 회차마다 달라짐 |
| 구조 해석 | 3회차가 격자를 행 단위로 해석 | **동일 코드가 정반대로 판정됨** |

**추가 분석 — 원인이 1단계에 있었을 가능성**

3회차에서 `list-grouping`(그룹 3개)와 `layout-result`(행 계층 포함)가 **함께** 나타났습니다. 2단계가 독립적으로 두 번 오판했다기보다, **1단계 구조 트리에 이미 행 계층이 포함되어 있었다고 보는 편이 자연스럽습니다.**

이 경우 2단계의 `accept` 다중 해석은 무력합니다. 받은 트리에 행 계층이 있으면 평면 해석이 존재한다는 것을 알 수 없어 나열할 재료가 없습니다.

**대응:** 1단계 프롬프트에 격자 구조를 평면으로 세도록 지시를 추가했습니다(프롬프트 v6). 모호성이 1단계에서 확정되지 않고 2단계로 내려가야 `accept`가 기능합니다.

**주의:** v5 재검증에서 재현성이 개선된 것은 `accept` 도입의 효과가 아니라 1단계가 3회 모두 평면으로 읽은 결과일 수 있습니다. 프롬프트 v6 적용 후 재측정이 필요합니다.

**대응 — 원인이 둘로 나뉩니다**

`list-grouping`의 그룹 단위 차이는 진짜 해석 불일치입니다. 렌더 결과가 같아도 DOM 구조가 실제로 다르고 시안으로 판별할 수 없으므로, 4.6.4의 다중 해석 허용(`accept` 배열)으로 대응합니다.

`layout-result`의 차이는 해석 불일치가 아닙니다. `1열 3행 + 행 내부 2열`은 DOM 중첩 구조를 배치 조건에 기술한 것으로, 4.6.3의 기존 규칙 위반입니다. 기대값을 말단 요소의 기하로만 기술하도록 강제하면 해소되며, 다중 해석은 필요하지 않습니다.

조건 개수 불일치는 별도 사안입니다. `heading-hierarchy`가 누락되면 검사가 하나 줄어들 뿐 잘못된 판정을 내리지는 않으므로, 미탐 방향의 손실로 분류하고 8.2에서 측정합니다.

### 8.4 레이아웃 측정 통로 — 해결 완료

**결론: 4.6.5의 레이아웃 판정 방식은 재설계가 불필요합니다.** 조건 유형 `layout-result`를 그대로 사용합니다.

`allow-same-origin`과 `allow-scripts`가 독립 플래그라는 점을 이용해, `allow-same-origin` 단독 부여로 측정 통로를 확보하면서 스크립트는 전면 차단합니다. 측정 스크립트 주입이 불필요하므로 당초 우려했던 쟁점(주입 스크립트만 선별 실행)이 발생하지 않습니다.

판정용 iframe은 미리보기와 분리하여 고정 폭으로 운영합니다. 측정값의 결정성 확보가 목적입니다.

상세 설계와 검증 결과는 4.6.5를 참조하십시오.

### 8.5 실제 시안 검증 — 완료

8.1~8.4는 더미 시안 한 장으로 측정했습니다. 실제 웹페이지 시안 두 장으로 다시 확인했습니다.

**검증 대상**

| 시안 | 규모 | 결과 |
|---|---|---|
| 패션 브랜드 페이지 | 1920×8486, 구역 11개 | 전 항목 통과 |
| 강의 랜딩 페이지 | 1920×27108, 구역 20개 | 종횡비 한계로 분석 불가 — 4.1의 상한 근거가 됨 |

**닫힌 항목**

| 항목 | 결과 |
|---|---|
| 구역 분할 정확도 | 시각적 구분과 일치. `bounds` 오차 최대 35px / 7072px = 0.5%로 오버레이 어긋남 없음 |
| 격자 평면 고정 | 유지. 행 계층 생성 0건 |
| 화이트리스트 준수 | 이탈 0건 |
| `layout-result` 대상 단위 | 전부 반복 항목으로 잡힘. 8.3의 프롬프트 수정이 실제 시안에서도 유지됨 |
| `form-label` | 실제 폼에서 3곳 생성 (사이즈 선택 2, 소식지 구독 1) |
| 모범 예시가 조건을 만족하는가 | 11구역 전부 통과. 결합 문서에서 `heading-single`·`heading-order`도 통과 |
| 통짜 모드 | 학습 흐름을 끝까지 확인. 기능은 정상이나 규모 제한이 필요 — 6.6 참조 |
| IndexedDB 용량 | 할당량 3.2GB 중 0.03% 사용. 실제 시안 한 건이 883KB(이미지 831KB + 데이터 52KB)로 산술상 3,800건. **제약이 아님** |

**캐러셀 — 판단 결과**

좌우 화살표가 있는 슬라이드형 목록에서 AI는 **화면에 보이는 3개로 셌습니다.** 슬라이드 위치 표시 점이 3개인 것도 구조 트리에 별도로 인식했으나 총 개수로 환산하지 않았습니다.

이는 문제가 아닙니다. 학습자도 시안 이미지만 보므로 학습자에게 보이는 것도 3개이고, `list-grouping`이 ≥ 의미론이므로 3개 이상이면 통과합니다. 기대값과 학습자의 인식이 일치합니다.

**구역 20개 초과 시 오버레이 — 판단 결과**

이름표 겹침은 발생하지 않습니다. 시안이 길수록 렌더 높이도 함께 커져 상쇄되기 때문입니다. 20구역 시안에서 이미지가 816×8355px로 렌더되고 편집 열이 스크롤하며, 이름표 높이 20px 대비 가장 작은 구역이 92px였습니다.

**남은 확인**

| 항목 | 아직 확인되지 않은 것 |
|---|---|
| 배포 | Vercel 환경에서의 환경 변수, 빌드, 전체 흐름 1회, IndexedDB 동작 |
