# HTML/CSS 학습 플레이그라운드 — 2단계 구현 요청

## 범위

**판정 엔진**입니다. AI 분석 연동은 다음 단계이며, 이번에는 **손으로 작성한 조건 JSON**으로 판정 로직을 검증합니다.

AI 연동을 뒤로 미루는 이유가 있습니다. 판정이 제대로 동작하는지 확인하기 전에 AI를 붙이면, 실패했을 때 원인이 판정 로직인지 AI 출력인지 구분할 수 없습니다.

상세 사양은 `docs/PRD.md`를 참조해 주세요. 특히 §4.6.4(조건 유형 정의), §6(데이터 구조), §8.2(검증 설계)입니다.

## 이번 단계에서 만드는 것

1. 조건 유형 상수와 스키마 검증
2. 판정 엔진 (7개 유형)
3. 판정용 iframe과 측정
4. 결합 판정
5. 실패 문구·힌트 생성
6. 판정 결과를 하단 패널에 표시

## 이번 단계에서 만들지 않는 것

- AI 분석 연동 (3단계)
- 소스 등록 화면 (3단계)
- 구역 편집 화면 (3단계)

---

## 1. 조건 유형 상수 (F-02-15)

**단일 상수에서 두 산출물을 파생합니다.**

```
조건 유형 상수 (단일 정의)
├─ 스키마 검증용 열거형
└─ 프롬프트 주입 텍스트 (3단계에서 사용)
```

두 곳에 따로 정의하면 어긋납니다. 주입 텍스트는 이번 단계에서 쓰이지 않지만, 상수 구조는 지금 잡아두는 편이 낫습니다.

유형 목록은 PRD §4.6.4의 정의표를 그대로 옮겨 주세요. **이번 단계는 6개입니다.**

| 생성 주체 | 유형 | 처리 |
|---|---|---|
| 엔진 상시 | `heading-order`, `heading-single` | rubric에 없음. 항상 검사 |
| AI 생성 | `image-alt`, `list-grouping`, `form-label`, `layout-result` | rubric에서 읽어 검사 |
| 보류 | `heading-hierarchy` | **이번 단계에서 제외** |

`heading-hierarchy`는 구조 패턴으로 정의하려면 두 대상을 특정해야 해서 다른 유형과 성격이 다릅니다. 구역 제목과 항목 제목의 관계는 `heading-order`가 상당 부분 포착하므로, 6개로 검증한 뒤 실제 필요성을 판단합니다.

## 2. 스키마 검증 (F-02-11, F-02-12)

조건 JSON을 판정에 넘기기 전에 검증합니다.

| 검사 | 실패 시 |
|---|---|
| `level: required`의 `type`이 열거형에 속하는가 | 조건 거부 |
| 유형이 요구하는 `accept` 파라미터가 존재하는가 | 조건 거부 |
| `layout-result`의 `accept`가 정확히 1개인가 (F-02-14) | 조건 거부 |
| `mainTitleSectionId`가 존재하는 구역을 가리키는가 (F-02-16) | 전체 거부 |

거부 시 로그를 남기고, 필수 조건이 하나도 남지 않은 구역은 오류로 처리합니다.

**`desc`는 검증하지 않고 판정에도 쓰지 않습니다.** 표시 전용입니다.

## 3. 판정 엔진

### 3.1 유형별 판정

각 `type`에 대응하는 판정 함수를 고정 정의합니다. **`desc`와 `target` 문자열을 읽지 않습니다.**

| type | 검사 | 입력 |
|---|---|---|
| `heading-order` | 제목 레벨이 2 이상 건너뛰지 않는지 | 결합 문서 |
| `heading-single` | `h1`이 정확히 1개인지 | 결합 문서 |
| `image-alt` | 구역 내 모든 의미 있는 이미지에 `alt` 존재 | 현재 구역 |
| `list-grouping` | 구역 내에 N개 동일 구조 항목을 담은 목록 존재 | 현재 구역 |
| `form-label` | 구역 내 모든 폼 컨트롤에 레이블 연결 | 현재 구역 |
| `layout-result` | N개 형제 말단 요소의 렌더 측정값이 기대 배치와 일치 | 현재 구역 (측정) |

### 3.2 대상 지정 — 구조 패턴으로만

**`target`은 판정에 쓰지 마십시오.** 구조 트리의 역할명(예: "제품 타일")이라 학습자 코드에 존재하지 않는 문자열이며, 태그와 클래스 이름이 자유 등급이라 셀렉터로 삼을 수 없습니다.

특정 요소를 지목하지 않고 **구역 범위 내의 구조 패턴**으로 검사합니다.

| 잘못된 접근 | 올바른 접근 |
|---|---|
| `target`이 가리키는 이미지를 찾아 `alt` 검사 | 구역 내 모든 이미지에 `alt`가 있는지 검사 |
| `target` 목록의 항목 수를 셈 | 구역 내에 `itemsPerGroup`개 항목을 담은 목록이 `groupCount`개 있는지 검사 |

`target`은 `desc`와 함께 표시 문구용으로만 유지합니다.

### 3.3 accept 판정

`accept` 배열 중 **하나라도** 만족하면 통과입니다.

`list-grouping`은 복수 항목을 가질 수 있습니다. 격자 구조에서 반복 단위 해석이 갈리기 때문입니다(§4.6.4).

```json
"accept": [
  { "groupCount": 1, "itemsPerGroup": 6 },
  { "groupCount": 3, "itemsPerGroup": 2 }
]
```

`layout-result`는 항상 1개입니다.

### 3.4 판정 결과 형태

어떤 조건이 왜 실패했는지 알 수 있어야 합니다. 통과 여부만 반환하면 실패 문구를 만들 수 없습니다.

각 조건별로 `type`, 통과 여부, 실패 시 실제 측정값(기대값과 대비할 수 있도록)을 담아 주세요.

## 4. 판정용 iframe (F-05-04 ~ F-05-06)

**미리보기 iframe과 별개로 운영합니다.**

| 항목 | 값 |
|---|---|
| `sandbox` | `allow-same-origin` (⚠️ `allow-scripts` 부여 금지) |
| CSP | `script-src 'none'` 함께 주입 |
| 숨김 방식 | **화면 밖 배치** (`position:absolute; left:-10000px`) |
| 너비 | 시안 기준 고정 |
| 생명주기 | 확인 시점에 생성, 측정 후 파기 |
| 측정 시점 | `load` 이벤트 이후 |

### 주의 사항 (실측으로 확인된 것들)

**`display:none`을 쓰면 안 됩니다.** 레이아웃 박스가 생성되지 않아 모든 측정값이 0이 되고, 오류 없이 `layout-result`가 무조건 통과합니다. 배치가 완전히 틀린 코드도 통과합니다.

**`allow-scripts`를 함께 주면 안 됩니다.** `allow-same-origin` 단독으로 부모에서 `contentDocument` 접근이 가능하며, 스크립트는 실행되지 않습니다. 측정 스크립트를 주입할 필요가 없습니다.

**미리보기(3열)는 `sandbox=""`를 유지합니다.** 완화된 오리진을 갖는 문서는 판정 순간에만 존재해야 합니다.

측정은 `getBoundingClientRect()`와 `getComputedStyle()`로 수행합니다.

## 5. 결합 판정 (F-08-05 ~ F-08-10)

`heading-single`과 `heading-order`에만 적용합니다.

```
결합 대상 = 아래를 order 순으로 정렬해 이어붙인 HTML

  status = passed    → code.html
  status = revealed  → example.html   ← 학습자 코드 아님
  현재 구역          → 작성 중인 code.html
```

| 규칙 | 내용 |
|---|---|
| 순서 | **현재 구역은 자기 `order` 자리.** 맨 뒤가 아님 |
| 범위 | 현재 구역보다 뒤에 있는 통과 구역도 포함 |
| CSS | **결합하지 않음** (F-08-07) |
| 시작 구역 | `mainTitleSectionId` 구역부터. 이전 구역은 건너뜀 |

`revealed` 구역에 `example.html`을 쓰는 이유는 §6.5에 있습니다. 학습자 코드를 쓰면 그 구역의 위반이 이후 전 구역으로 전파되어 무엇을 작성해도 통과할 수 없게 됩니다.

**요구:** 결합에 예시 코드가 포함된 경우 화면에 그 사실을 표시해야 합니다(F-08-08).

## 6. 실패 문구와 힌트 (F-07-01, F-07-07, F-07-08)

### 6.1 실패 문구

`type`별 고정 템플릿에 `accept` 파라미터를 넣어 생성합니다. **`desc`를 그대로 표시하지 마십시오.**

판정과 표시 문구가 어긋나면 학습자가 무엇을 고쳐야 할지 알 수 없습니다.

### 6.2 회차별 힌트

| 회차 | 수위 |
|---|---|
| 1 | 위치만 |
| 2 | 위치 + 방향 |
| 3 | 구체적 |

AI 생성 조건은 `rubric[].hints`에서 읽습니다.

**엔진 상시 조건(`heading-single`, `heading-order`)은 `hints`가 없으므로 코드에 고정 정의합니다**(F-07-08). 파라미터가 없고 검사 내용이 고정이라 힌트도 고정할 수 있습니다.

```
heading-single 예
1회차: 문서 전체의 제목 구조를 확인해보세요.
2회차: 페이지에서 가장 상위 제목이 몇 개인지 세어보세요.
3회차: 최상위 제목은 문서에 하나만 두어야 합니다.
```

시도 횟수를 1~2회로 설정한 경우 수위 단계를 압축 적용합니다.

## 7. 화면 연결

1단계에서 만든 하단 피드백 패널에 판정 결과를 표시합니다.

- 확인 버튼 활성화
- 실패 조건 목록과 회차별 힌트
- 남은 시도 횟수 갱신
- 시도 소진 시 모범 예시 공개 (**복사 기능 없음** — F-07-05)
- 피드백 항목 클릭 시 해당 코드 줄로 이동 (F-07-03, 권장)

권장 등급 조건은 통과시키되 안내 문구를 함께 표시합니다.

## 8. 테스트 픽스처

AI 연동 전이므로 조건 JSON을 손으로 작성해야 합니다. **§8.2 검증에 그대로 쓸 수 있는 형태로 만들어 주세요.**

`public/sample-design.svg`(0단계에서 만든 더미 시안)를 대상으로 합니다.

| 픽스처 | 용도 |
|---|---|
| 정답 코드 (3~4벌) | **시안만 보고 작성** — 오탐 측정 |
| 조건 JSON | 6개 유형 포함 |
| 위반 코드 | 각 조건을 의도적으로 위반 — 미탐 측정 |

**작성 순서가 중요합니다.**

1. `public/sample-design.svg`만 보고 정답 코드 3~4벌을 먼저 작성하고 **커밋**
2. 그 다음 조건 JSON 작성
3. 위반 코드는 조건을 보고 작성해도 무방 (의도적 위반이 목적)

조건을 알고 정답 코드를 쓰면 기대값이 틀린 경우를 잡을 수 없어, 검증이 스스로를 검증하는 구조가 됩니다(§8.2). **커밋 순서가 독립성의 증거로 남습니다.**

미탐 측정 항목은 §8.2에 목록이 있습니다. 특히 `accept`가 과도하게 넓어 위반 코드가 통과하는지를 확인해 주세요.

## 9. 작업 순서

각 단계마다 동작 확인 후 다음으로 넘어가고, 커밋을 나눠 주세요.

1. 조건 유형 상수 + 스키마 검증
2. 판정용 iframe + 측정 (`display:none` 금지, `allow-scripts` 금지 확인)
3. 유형별 판정 함수 (엔진 상시 2개 + AI 생성 5개)
4. 결합 판정
5. 실패 문구 + 힌트 생성
6. 화면 연결
7. 정답 코드 픽스처 작성 (시안만 보고, 별도 커밋)
8. 조건 JSON + 위반 코드 픽스처
9. §8.2 검증 실행

**9번의 검증 결과를 반드시 공유해 주세요.** 오탐률과 미탐률이 이 프로젝트가 성립하는지를 결정합니다.
