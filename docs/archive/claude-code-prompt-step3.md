# HTML/CSS 학습 플레이그라운드 — 3단계 구현 요청

## 범위

**AI 분석 연동**입니다. 2단계에서 만든 판정 엔진에 실제 AI 출력을 연결하고, 사용자가 시안을 등록해 학습을 시작할 수 있게 만듭니다.

마지막 작업은 **§8.2 재측정**입니다. 2단계의 오탐 0/5, 미탐 0/9는 손으로 쓴 조건으로 얻은 수치이며, AI 조건에서 같은 결과가 나오는지가 이 프로젝트의 성립 여부를 결정합니다.

상세 사양은 `docs/PRD.md`, 프롬프트는 `docs/analysis-prompt.md`를 참조해 주세요.

## 만드는 것

2. 소스 등록 화면
3. 구역 편집 화면
4. 진행 상태 저장 (IndexedDB)

## 0. 두 보류 건에 대한 결정

**`heading-hierarchy`는 계속 보류합니다.**

6개 유형으로 오탐 0, 미탐 0이 나왔고, `heading-order`가 실제로 제목 관계를 포착했습니다(V4, V5의 부가 실패). 필요하다는 증거가 없는 상태에서 유형을 늘리면 오탐 표면만 넓어집니다. `status: "deferred"`를 유지해 주세요.

**F-07-03도 계속 보류합니다.**

판정 함수가 위반 요소를 반환하도록 확장하는 것은 구조 변경입니다. AI 연동이라는 더 큰 변수를 다루는 단계에서 함께 건드릴 사안이 아닙니다.

## 1. AI 분석 연동

### 1.1 호출 구조

프롬프트가 3단계로 나뉘어 있습니다. **한 번에 합치지 마십시오.**

```
1단계  구조 분석      이미지 → 구역·구조·mainTitleSectionId
2단계  조건 생성      1단계 출력 → rubric
3단계  모범 예시      2단계 출력 → example.html/css
```

**분리 이유:** 조건과 예시를 한 호출에서 만들면 AI가 자기가 쓴 코드를 설명하는 조건을 생성합니다. 그러면 "예시와 다르면 오답"이 되어 다양성 대응이 무너집니다.

### 1.2 서버 측 처리

API 키는 서버에만 둡니다. Next.js Route Handler로 프록시합니다.

- 이미지는 base64로 전달
- 각 단계 실패 시 재시도 (F-02-07)
- 3단계 전체 실패 시 등록을 롤백

### 1.3 프롬프트 주입

`buildPromptConditionTypeTable()`을 `{{CONDITION_TYPES}}` 자리에 넣습니다.

`docs/analysis-prompt.md`의 2단계에서 **"heading-single과 heading-order는 생성하지 마십시오" 문장을 삭제해 주세요.** 주입 표에 애초에 없으므로 불필요합니다.

### 1.4 검증

`validateAnalysis()`를 그대로 사용합니다. AI 출력이 들어오는 자리가 이미 이 함수입니다.

거부가 발생하면 **로그만 남기지 말고 화면에 알려 주세요.** 등록 시점에 조건이 부실하면 학습 내내 영향을 받습니다.

## 2. 소스 등록 화면 (F-01)

| 항목 | 내용 |
|---|---|
| 업로드 | PNG, JPG |
| 모드 선택 | 통짜 / 구역별 |
| 시도 횟수 | 1~5, 기본 3 |
| 저작권 고지 | 업로드 소스의 책임은 사용자에게 있음 |
| 분석 진행 표시 | 3단계 호출이 수 초 걸립니다 |
| 소스 목록 | 재진입, 삭제 |

Figma 연동(F-01-02)은 이번 범위에서 제외합니다. 학습 목표가 시맨틱·레이아웃이므로 이미지만으로 충분하며(§4.1), 연동 자체가 별도 작업량입니다.

**이미지 용량:** IndexedDB에 Blob으로 저장하므로 등록 시 리사이즈나 WebP 변환을 검토해 주세요. 고해상도 PNG 여러 장이면 할당량에 걸립니다.

## 3. 구역 편집 화면 (F-03)

학습 화면 진입 전 별도 단계입니다.

```
┌────────────────────────────┬───────────────────────────┐
│  시안 + 오버레이            │  구역 목록                 │
│  (구역이 반투명 박스로)      │  선택 구역 조작 패널        │
└────────────────────────────┴───────────────────────────┘
```

| 기능 | 우선순위 |
|---|---|
| AI 분할 결과를 오버레이로 표시 | 필수 |
| 조정 없이 진행 가능 | 필수 |
| 인접 구역 병합 | 필수 |
| 구역 분할 | 필수 |
| 경계선 드래그 | 필수 |
| 구역 이름 편집 | 권장 |

`bounds`가 비율이므로 이미지 크기에 맞춰 환산합니다.

**병합·분할 시 rubric 처리를 정해야 합니다.** 두 구역을 합치면 조건이 합쳐지는데, `layout-result`의 기대값이 구역 범위를 전제하므로 그대로 이어붙이면 맞지 않을 수 있습니다. 어떻게 처리할지 판단해 알려 주세요.

## 4. 진행 상태 저장 (F-08-04)

현재 `attemptsUsed`와 판정 결과가 화면 상태로만 있습니다. PRD §6.4 구조로 저장 계층에 연결합니다.

| 대상 | 저장소 |
|---|---|
| 시안 이미지 (Blob) | IndexedDB |
| 분석 결과, rubric, example | IndexedDB |
| 구역별 code, status, attemptsUsed | IndexedDB |
| needsRecheck, recheckCause | IndexedDB |
| 에디터 설정 | localStorage 유지 |

1단계 저장 계층이 Promise 인터페이스이므로 IndexedDB 교체가 자연스럽게 이어집니다.

**F-08-06 재검증도 여기서 구현됩니다.** 선행 구역 변경 시 후속 구역에 `needsRecheck` 표시를 남기되, 통과 상태와 개방은 유지합니다.

**복원 직후 재기록** — 1단계 마무리 때 남기신 항목입니다. 저장값과 같으면 쓰기를 건너뛰도록 처리해 주세요.

## 5. §8.2 재측정

**이번 단계에서 가장 중요한 작업입니다.**

`/dev/verify`의 `SAMPLE_ANALYSIS`를 AI 출력으로 교체하고, 2단계에서 만든 정답 4벌 + 위반 9건을 그대로 돌립니다.

### 예상

**수치가 나빠질 가능성이 높습니다.** §8.3에서 이미 확인된 문제들이 있습니다.

| 문제 | 예상 영향 |
|---|---|
| 유형 오용 (`type`은 유효하나 `desc`가 다른 조건) | 판정에는 영향 없음 (`desc` 미사용). 표시 문구만 어긋남 |
| 재현성 불안정 (조건 개수가 회차마다 다름) | 검사가 줄어 미탐 방향 손실 |
| 기대값 오독 (3열 2행을 2열 3행으로) | **오탐 직결.** 판정 계층에서 차단 불가 |

세 번째가 핵심입니다. 고정 코드는 잘못된 기대값을 충실히 판정하므로, 정답 코드가 실패합니다.

### 측정 방식

같은 시안을 **3회 분석해 각각으로 §8.2를 돌려 주세요.** 회차마다 결과가 다르면 그 자체가 재현성 문제의 증거입니다.

`(type, 파라미터)` 집합으로 회차 간 조건을 비교하고, `desc` 문구 차이는 불일치로 세지 않습니다.

### 결과 해석

수치가 나쁘게 나와도 그것이 이번 단계의 실패는 아닙니다. **어디서 나빠졌는지가 중요합니다.**

- 판정 엔진 문제인가 → 2단계에서 오탐 0이었으므로 가능성 낮음
- AI 조건 문제인가 → 프롬프트 개선 여지
- 구조적 한계인가 → 설계 재검토

원인을 구분해서 보고해 주세요.
